# Content: каталог публикаций

Go-сервис хранит приватные черновики и публикации, связывает их с файлами и выбирает кандидатов для лент видео, фото и автора. Сессии и аккаунты проверяются через user/auth, приём файлов выполняет media-processing. Рекомендации, проверка прав при выдаче лент, продажи, реклама и клиенты в разработке.

Схема `content_posts` хранит автора, тип (`video` или `photo`), заголовок, описание, видимость и состояние. `content_post_media` связывает публикацию с UUID файлов без хранения байтов. По умолчанию запись — приватный черновик. Переход в `published` выполняется внутренним методом после проверки прав и готовности файлов. Проверки модерации будут добавлены на отдельном этапе. Обычная роль приложения может вставлять только разрешённые колонки приватного черновика и не должна иметь права изменения статуса, видимости, связей медиа или удаления; отдельная роль выполняет окончательную очистку. Посторонним ролям запись не предоставляется.

Внутренний `GET /internal/feed` отдаёт только идентификаторы публичных опубликованных кандидатов и время публикации. `kind=video`, `kind=photo` или отсутствие `kind` выбирает видео, фото или смешанную ленту. `author=<UUID>` ограничивает выдачу автором, `limit` — от 1 до 100. Для следующей страницы передайте вместе `before_time` в RFC3339 и `before_id` последнего результата. Одинаковые даты упорядочиваются по UUID; изменение времени публикации между страницами может влиять на выдачу. Это хронологические кандидаты, не персональные рекомендации.

Для `GET /internal/feed/posts` фильтры те же, но предел страницы 40. В ответе `posts` с данными карточек и `next` с последней позицией, если есть следующая страница. Это внутренний контракт: перед выдачей карточек user проверяет профили и активность аккаунтов в auth и преобразует позицию в зашифрованный курсор.

Для запроса необходим `X-Internal-Secret`. Запрос доступен только на loopback, а сам ответ не является решением о правах или разрешением на скачивание: до показа нужно повторно проверить актуальные права и состояние через auth/user. Платные, приватные и неопубликованные записи в эту выдачу не входят. Для платных публикаций отдельно нужны безопасный preview, учёт покупки и проверка доступа; пока они не разработаны. При недоступности БД запрос возвращает 503. `/health` проверяет процесс, но не готовность БД.

## Запуск и конфигурация

Сервис читает `[database]`, `[resources]` и `[services.content]` из общего `config.toml`; на отдельном сервере допустим файл только с нужными секциями. Используются общие пользователь и пароль БД, либо отдельная пара в `[services.content.database]`. Нужны собственная база, отдельные роли мигратора и runtime, а также отдельный случайный `internal_secret` длиной 32–128 печатных ASCII-символов. Пустой секрет запрещает запуск. Для ротации `internal_secret_previous` временно принимает старый ключ; все экземпляры должны принимать оба ключа до переключения вызывающих сервисов. Конфиг хранится вне Git с ограниченными правами.

Пример настроек сервиса:

```toml
[services.content]
host = "127.0.0.1"
port = 8083
internal_secret = "ЗАМЕНИТЬ_НА_СЛУЧАЙНЫЙ_СЕКРЕТ"
internal_secret_previous = ""
purge_secret = "ЗАМЕНИТЬ_ОТДЕЛЬНЫМ_СЛУЧАЙНЫМ_КЛЮЧОМ"
purge_secret_previous = ""
max_connections = 128
recovery_mode = false

[services.content.user]
url = "http://127.0.0.1:8081"
cookie_name = "__Host-mtls_session"

[services.content.database]
host = "127.0.0.1"
name = "mtls_content"
user = "content_app"
password = "ЗАМЕНИТЬ"
purge_user = "content_purger"
purge_password = "ЗАМЕНИТЬ"
```

Создайте БД и примените миграцию командой `go run ./content/cmd/migrate -config ../config.toml` из каталога `backend`. Затем запускайте `go run ./content/cmd/server -config ../config.toml`. Обычной runtime-роли нужны SELECT на четыре таблицы (`content_posts`, `content_post_media`, `content_draft_requests`, `content_author_purges`), INSERT только в колонки `id`, `author_id`, `media_kind`, `title`, `description` таблицы `content_posts`, UPDATE только колонок `title`, `description`, `revision` этой таблицы и INSERT в `content_draft_requests`. Триггер миграции `004` разрешает такое изменение лишь приватному черновику с увеличением версии; сервер проверяет его наличие и включение. Отдельной роли очистки нужны SELECT на те же четыре таблицы, DELETE на `content_posts`, `content_draft_requests` и `content_author_purges`, INSERT только колонки `author_id` в `content_author_purges` и UPDATE только колонки `created_at` в `content_posts` для блокировки строк. DDL выполняет третья роль — мигратор. Сервер отказывается запускаться при отсутствии необходимых или наличии опасных прав, а также если роль владеет таблицами или является суперпользователем. Для удалённой PostgreSQL обязателен `sslmode=verify-full`. Сервер пока принимает только loopback: межсерверные TLS/mTLS, отдельные идентичности вызывающих сервисов и публичный API не реализованы. `max_connections` ограничивает TCP-соединения; запрос к БД ограничен пятью секундами. Нулевые значения `resources` оставляют настройки runtime Go по умолчанию.

План пользовательских сценариев, продаж и рекламы — в корневом `TASKS.md`; открытые баги — в `BUGS.md`.

## Черновики и очистка

Доверенный клиент вызывает `POST /internal/drafts` с `X-Internal-Secret`, cookie сессии и JSON `request_id` (UUID), `kind` (`photo` или `video`), `title` и `description`. Author ID берётся только из user/auth; переданный клиентом `author_id` отклоняется. Повтор того же `request_id` с теми же данными возвращает тот же UUID; другой текст с тем же ID возвращает 409. Черновик остаётся приватным, привязка и публикация медиа пока не реализованы. При недоступности user запрос возвращает 503.

`GET /internal/drafts` возвращает только приватные черновики владельца проверенной сессии. Необходимы тот же внутренний ключ и cookie. `limit` по умолчанию равен 20, максимум — 100; для следующей страницы вместе передаются `before_time` (поле `created_at` последней записи в RFC3339) и `before_id`. Результаты упорядочены по времени создания и UUID по убыванию. Идентификатор автора в запросе не принимается; при недоступности user возвращается 503. Для этой выборки перед запуском применяется миграция `003`; создание индекса обычной миграцией может блокировать запись в большую существующую таблицу, поэтому обновление необходимо планировать с учётом её размера.

`PUT /internal/drafts/{id}` меняет текст только своего приватного черновика. Нужны ключ, cookie и JSON с обязательными `revision`, `title`, `description`; версия берётся из списка. При успехе возвращается новая версия, при устаревшей — 409, при отсутствии доступного черновика — 404. После потерянного ответа повтор с прежней версией также вернёт 409: клиент должен получить актуальный черновик и сверить данные. Публикация, изменение видимости и медиа этим методом невозможны.

Окончательное удаление аккаунта ставит в user очередь очистки content. Для неё используются отдельное соединение с ролью БД `purge_user`/`purge_password` и **отдельный** `purge_secret`, отличный от ключа ленты и всех его версий; старый ключ можно временно задать как `purge_secret_previous`. В user настройте `services.user.content.url` и тот же ключ через общий `[services.content].purge_secret` либо отдельную настройку user. Если publisher отключён или content недоступен, событие остаётся в очереди и должно быть обработано после восстановления; без настроенного publisher автоматической очистки нет.

Content удаляет черновики и их idempotency-записи порциями до 500 публикаций в транзакции. На время неполной очистки сохраняется маркер автора, запрещающий создание новых черновиков. Content возвращает 202, user сохраняет задачу и повторяет следующий шаг через секунду; 204 означает завершение, 503 сохраняет задачу для повтора после ошибки. После завершения маркер удаляется. User не отправляет очистку content, пока у автора есть политики файлов, включая непривязанные загрузки. Если у автора всё же есть связанные медиа, content возвращает ошибку и сохраняет ссылки до реализации удаления файлов; так UUID не теряются, но полное удаление пока не завершено. Уже начатые потоки, файлы на диске, реплики, кэши и резервные копии требуют отдельного проверенного жизненного цикла.

После восстановления content из старой копии обязательна офлайн-сверка с независимо проверенной актуальной auth-БД по `backend/OPERATIONS.md`. До её успешного завершения восстановленный сервис должен оставаться изолированным; автоматической проверки полноты источника пока нет.

Для запуска восстановленного экземпляра в изолированной сети установите `[services.content].recovery_mode = true` в его конфигурации. В этом режиме работает только `GET /health`, остальные API возвращают 503. Перед офлайн-сверкой остановите все экземпляры и закройте другие соединения с обеими БД. Флаг не обнаруживает восстановление автоматически и не ограничивает прямой доступ к БД; оставляйте его включённым, пока полнота auth не подтверждена и сверка не завершена.

## Индекс публикаций

Миграция `005` добавляет outbox: в индекс передаётся только заголовок опубликованного публичного материала, при скрытии или удалении создаётся tombstone. События фиксируются в той же транзакции, что и изменение публикации. Индекс содержит только кандидатов: проверка текущих прав через auth/user перед выдачей результатов ещё не реализована, поэтому внешний поиск публикаций не включён.

Издатель запускается отдельно из `backend` командой `go run ./content/cmd/search-publisher -config ../config.toml`. Ему требуются PostgreSQL 15 или новее, отдельная роль БД и отдельный ключ записи `content_writer_secret` search. Пример для отдельного защищённого файла конфигурации издателя:

```toml
[services.content.search]
url = "http://127.0.0.1:8085"
writer_secret = "ОТДЕЛЬНЫЙ_КЛЮЧ_CONTENT_ИЗ_SEARCH"
database_user = "content_search_publisher"
database_password = "ЗАМЕНИТЬ"
```

Роли издателя дайте `USAGE` на схему, `SELECT` и `DELETE` на `content_search_events`, а также `UPDATE` только колонок `lease_token` и `lease_until`. Ролям приложения и очистки не разрешайте менять outbox; никто из этих процессов не должен владеть схемой, функцией или таблицами, иметь `CREATE` в `public`, `BYPASSRLS`, `SET session_replication_role` или быть суперпользователем. Эти ограничения и включённые триггеры проверяются при запуске. Секрет, пароль роли и доступ к конфигу ограничьте процессом издателя. Текущий канал к search поддерживает только loopback; для разных серверов нужны mTLS и проверка идентичности.

При отказе search событие сохраняется и повторяется после истечения аренды. При восстановлении content или search остановите **все** экземпляры издателя и включите `recovery_mode` в его конфигурации до сверки: уже запущенный процесс не перечитывает конфигурацию. Автоматической защиты от отката источника и полной процедуры восстановления индекса публикаций пока нет; риск и ограничения — в `BUGS.md`.

Внутренний `POST /internal/search/recheck` с `X-Internal-Secret` и JSON `{"query":"...","ids":["UUID"]}` возвращает совпадающие актуальные публичные публикации в порядке кандидатов. Метод ограничен 50 ID и не является проверкой сессии или активности автора; эти проверки выполняет user через auth.

Миграция `006` добавляет замену вложений приватного черновика. Приложению требуется `EXECUTE` на `public.content_set_draft_media(uuid,uuid,bigint,uuid[])`. Прямые права записи в `content_post_media` по-прежнему запрещены, роль очистки команду не выполняет.

Внутренний `PUT /internal/drafts/{id}/media` принимает `{"revision":1,"media_ids":["UUID"]}` и возвращает текущую ревизию. Порядок сохраняется, допускается до 16 уникальных ID. Пустой список отсоединяет файлы. Действуют обычные внутренний секрет и cookie. Content перепроверяет в user, что каждый файл готов и принадлежит автору. Черновики возвращают `media_ids` внутри `GET /internal/drafts`. Отзыв между проверкой и сохранением может оставить устаревшую ссылку в приватном черновике. При публикации состояние, тип и право на каждый файл нужно проверить снова.

Внутренний `POST /internal/drafts/{id}/publish` принимает `{"revision":2,"visibility":"public"}`. По умолчанию видимость `private`. Перед записью content проверяет заголовок, готовность, владельца и тип всех вложений. Повтор с той же исходной ревизией и видимостью переиспользует переход, пока вложения остаются доступными. Public создаёт событие для поискового индекса. `GET /internal/posts/{id}` возвращает приватную публикацию только автору, а публичную также активному вошедшему зрителю после проверки обоих аккаунтов в user/auth. Для обоих методов нужны внутренний секрет и сессия.

Кабинет автора может проверять файл отдельно. При просмотре публикации media вызывает user с ID публикации, а user проверяет конкретную привязку через `GET /internal/posts/{id}/media/{media}/access`. Content проверяет, что публикация ещё доступна зрителю и что владелец файла совпадает с её автором. Готовность файла и актуальность сессии проверяет user. Публичный режим сейчас требует действующую сессию. Доступ стороннего зрителя к платным публикациям появится после подключения прав покупки.

Для миграции `009` добавьте роли приложения `EXECUTE` на `public.content_publish_post(uuid,uuid,bigint,text)`. Роли очистки исполнение запрещено. Старый `public.content_publish_private(uuid,uuid,bigint)` оставлен для предыдущего бинарника. После его выключения можно отозвать прежний GRANT. Подключите описанный в user внутренний клиент content до публикации общедоступных материалов.

Внутренние `POST /internal/posts/{id}/remove` и `POST /internal/posts/{id}/restore` принимают `{"revision":2}` и возвращают новую ревизию. Для удаления из публичной выдачи транзакция записывает tombstone поиска. Восстановление возможно для записи, удалённой автором, и переводит её в приватный черновик. При публикации вложения перепроверяются. Повтор удаления с исходной ревизией безопасен, а повтор восстановления с устаревшей ревизией возвращает 409. Для миграции `008` добавьте роли приложения `EXECUTE` на `public.content_change_author_removal(uuid,uuid,bigint,boolean)`. Прямая запись в `author_removed_at` запрещена. Вложения остаются привязанными.

### Лайки и избранное

`PUT /internal/posts/{id}/like` и `PUT /internal/posts/{id}/favorite` добавляют реакцию, `DELETE` на том же маршруте снимает её. Запрос без тела требует внутренний секрет и сессию. Успешный повтор возвращает 204. Сервис проверяет в user/auth зрителя и автора, затем в транзакции сверяет, что публикация остаётся доступной. В данных публикации `likes` — число лайков, `liked` и `favorited` — признаки текущего зрителя.

Миграция `010` добавляет таблицы `content_post_likes`, `content_post_favorites` и `content_post_statistics`. Роли приложения нужны `SELECT` на них и `EXECUTE` на `public.content_set_reaction(uuid,uuid,uuid,text,boolean)`. Роли очистки нужен только `EXECUTE` на `public.content_purge_viewer_reactions(uuid)` в дополнение к прежним правам. Ни одной из этих ролей не давайте прямую запись в новые таблицы. При очистке аккаунта сервис удаляет лайки и избранное порциями, пересчитывает счётчики и продолжает существующее удаление публикаций. Окончательное удаление поста каскадно очищает его реакции.

`GET /internal/favorites?limit=20` возвращает закладки текущей сессии по времени добавления. `limit` от 1 до 40. Content проверяет текущую видимость поста и перед ответом одним запросом к user перепроверяет авторов. Если присутствует `next_cursor`, передайте его как `cursor`, даже если текущая страница пуста. Курсор зашифрован и привязан к владельцу списка.

### Просмотры

Миграция `011` добавляет счётчик `views` в данные публикации. Media отправляет событие после начала фактической выдачи файла. Content повторно проверяет привязку и текущую публичность поста и засчитывает одному зрителю один просмотр публикации за сутки UTC. Авторские просмотры исключаются. Запоздалое событие за вчера принимается, пока более свежий день для этой пары ещё не записан. Периодическая очистка удаляет просроченные записи дедупликации, а очистка аккаунта удаляет их по зрителю. Общие счётчики сохраняются без идентификаторов зрителей.

Укажите в `[services.content].media_view_secret` новый случайный секрет, совпадающий с `[services.media.views].secret`. Роли приложения нужны `EXECUTE` на `public.content_count_post_view(uuid,uuid,uuid,integer)` и `public.content_prune_view_receipts()`, роли очистки — `EXECUTE` на `public.content_purge_view_receipts(uuid)`. Обе роли работают без прямого доступа к таблице дедупликации.
