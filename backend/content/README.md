# Content: каталог публикаций

Go-сервис хранит приватные черновики и публикации, связывает их с файлами и выбирает кандидатов для лент видео, фото и автора. Сессии и аккаунты проверяются через user/auth, приём файлов выполняет media-processing. Рекомендации, проверка прав при выдаче лент, продажи, реклама и клиенты в разработке.

Схема `content_posts` хранит автора, тип (`video` или `photo`), заголовок, описание, видимость и состояние. `content_post_media` связывает публикацию с UUID файлов без хранения байтов. По умолчанию запись — приватный черновик. Переход в `published` выполняется внутренним методом после проверки прав и готовности файлов. Проверки модерации будут добавлены на отдельном этапе. Обычная роль приложения может вставлять только разрешённые колонки приватного черновика и не должна иметь права изменения статуса, видимости, связей медиа или удаления; отдельная роль выполняет окончательную очистку. Посторонним ролям запись не предоставляется.

Внутренний `GET /internal/feed` отдаёт только идентификаторы публичных опубликованных кандидатов и время публикации. `kind=video`, `kind=photo` или отсутствие `kind` выбирает видео, фото или смешанную ленту. `author=<UUID>` ограничивает выдачу автором, `limit` — от 1 до 100. Для следующей страницы передайте вместе `before_time` в RFC3339 и `before_id` последнего результата. Одинаковые даты упорядочиваются по UUID; изменение времени публикации между страницами может влиять на выдачу. Это хронологические кандидаты, не персональные рекомендации.

Для `GET /internal/feed/posts` фильтры те же, но предел страницы 40. В ответе `posts` с данными карточек и `next` с последней позицией, если есть следующая страница. Это внутренний контракт: перед выдачей карточек user проверяет профили и активность аккаунтов в auth и преобразует позицию в зашифрованный курсор.

Для запроса необходим `X-Internal-Secret`. Запрос доступен только на loopback, а сам ответ не является решением о правах или разрешением на скачивание: до показа нужно повторно проверить актуальные права и состояние через auth/user. Платные, приватные и неопубликованные записи в эту выдачу не входят. Для платных публикаций отдельно нужны безопасный preview, учёт покупки и проверка доступа; пока они не разработаны. При недоступности БД запрос возвращает 503. `/health` проверяет процесс, но не готовность БД.

## Запуск и конфигурация

Сервис читает `[database]`, `[resources]` и `[services.content]` из общего `config.toml`; на отдельном сервере допустим файл только с нужными секциями. Используются общие пользователь и пароль БД, либо отдельная пара в `[services.content.database]`. Нужны собственная база, отдельные роли мигратора и runtime, а также отдельный случайный `internal_secret` длиной 32–128 печатных ASCII-символов. Пустой секрет запрещает запуск. Для ротации `internal_secret_previous` временно принимает старый ключ; все экземпляры должны принимать оба ключа до переключения вызывающих сервисов. Конфиг хранится вне Git с ограниченными правами.

Пример настроек сервиса:

```toml
[services.content]
host = "127.0.0.1"
port = 8083
internal_secret = "ЗАМЕНИТЬ_НА_СЛУЧАЙНЫЙ_СЕКРЕТ"
internal_secret_previous = ""
purge_secret = "ЗАМЕНИТЬ_ОТДЕЛЬНЫМ_СЛУЧАЙНЫМ_КЛЮЧОМ"
purge_secret_previous = ""
max_connections = 128
recovery_mode = false

[services.content.user]
url = "http://127.0.0.1:8081"
cookie_name = "__Host-mtls_session"

[services.content.database]
host = "127.0.0.1"
name = "mtls_content"
user = "content_app"
password = "ЗАМЕНИТЬ"
purge_user = "content_purger"
purge_password = "ЗАМЕНИТЬ"
```

Создайте БД и примените миграцию командой `go run ./content/cmd/migrate -config ../config.toml` из каталога `backend`. Затем запускайте `go run ./content/cmd/server -config ../config.toml`. Обычной runtime-роли нужны SELECT на четыре таблицы (`content_posts`, `content_post_media`, `content_draft_requests`, `content_author_purges`), INSERT только в колонки `id`, `author_id`, `media_kind`, `title`, `description` таблицы `content_posts`, INSERT в `content_draft_requests` и EXECUTE для функций переходов. После миграции 029 редактирование выполняется через content_edit_post. Сервер проверяет границы полномочий и наличие триггера смены редакции. Отдельной роли очистки нужны SELECT на те же четыре таблицы, DELETE на `content_posts`, `content_draft_requests` и `content_author_purges`, INSERT только колонки `author_id` в `content_author_purges` и UPDATE только колонки `created_at` в `content_posts` для блокировки строк. DDL выполняет третья роль — мигратор. Сервер отказывается запускаться при отсутствии необходимых или наличии опасных прав, а также если роль владеет таблицами или является суперпользователем. Для удалённой PostgreSQL обязателен `sslmode=verify-full`. Сервер пока принимает только loopback: межсерверные TLS/mTLS, отдельные идентичности вызывающих сервисов и публичный API не реализованы. `max_connections` ограничивает TCP-соединения; запрос к БД ограничен пятью секундами. Нулевые значения `resources` оставляют настройки runtime Go по умолчанию.

План пользовательских сценариев, продаж и рекламы — в корневом `TASKS.md`; открытые баги — в `BUGS.md`.

## Черновики и очистка

Доверенный клиент вызывает `POST /internal/drafts` с `X-Internal-Secret`, cookie сессии и JSON `request_id` (UUID), `kind` (`photo` или `video`), `title` и `description`. Author ID берётся только из user/auth; переданный клиентом `author_id` отклоняется. Повтор того же `request_id` с теми же данными возвращает тот же UUID; другой текст с тем же ID возвращает 409. Черновик остаётся приватным, привязка и публикация медиа пока не реализованы. При недоступности user запрос возвращает 503.

`GET /internal/drafts` возвращает только приватные черновики владельца проверенной сессии. Необходимы тот же внутренний ключ и cookie. `limit` по умолчанию равен 20, максимум — 100; для следующей страницы вместе передаются `before_time` (поле `created_at` последней записи в RFC3339) и `before_id`. Результаты упорядочены по времени создания и UUID по убыванию. Идентификатор автора в запросе не принимается; при недоступности user возвращается 503. Для этой выборки перед запуском применяется миграция `003`; создание индекса обычной миграцией может блокировать запись в большую существующую таблицу, поэтому обновление необходимо планировать с учётом её размера.

`PUT /internal/drafts/{id}` меняет текст только своего приватного черновика. Нужны ключ, cookie и JSON с обязательными `revision`, `title`, `description`; версия берётся из списка. При успехе возвращается новая версия, при устаревшей — 409, при отсутствии доступного черновика — 404. После потерянного ответа повтор с прежней версией также вернёт 409: клиент должен получить актуальный черновик и сверить данные. Публикация, изменение видимости и медиа этим методом невозможны.

Окончательное удаление аккаунта ставит в user очередь очистки content. Для неё используются отдельное соединение с ролью БД `purge_user`/`purge_password` и **отдельный** `purge_secret`, отличный от ключа ленты и всех его версий; старый ключ можно временно задать как `purge_secret_previous`. В user настройте `services.user.content.url` и тот же ключ через общий `[services.content].purge_secret` либо отдельную настройку user. Если publisher отключён или content недоступен, событие остаётся в очереди и должно быть обработано после восстановления; без настроенного publisher автоматической очистки нет.

Content удаляет черновики и их idempotency-записи порциями до 500 публикаций в транзакции. На время неполной очистки сохраняется маркер автора, запрещающий создание новых черновиков. Content возвращает 202, user сохраняет задачу и повторяет следующий шаг через секунду; 204 означает завершение, 503 сохраняет задачу для повтора после ошибки. После завершения маркер удаляется. User не отправляет очистку content, пока у автора есть политики файлов, включая непривязанные загрузки. Если у автора всё же есть связанные медиа, content возвращает ошибку и сохраняет ссылки до реализации удаления файлов; так UUID не теряются, но полное удаление пока не завершено. Уже начатые потоки, файлы на диске, реплики, кэши и резервные копии требуют отдельного проверенного жизненного цикла.

После восстановления content из старой копии обязательна офлайн-сверка с независимо проверенной актуальной auth-БД по `backend/OPERATIONS.md`. До её успешного завершения восстановленный сервис должен оставаться изолированным; автоматической проверки полноты источника пока нет.

Для запуска восстановленного экземпляра в изолированной сети установите `[services.content].recovery_mode = true` в его конфигурации. В этом режиме работает только `GET /health`, остальные API возвращают 503. Перед офлайн-сверкой остановите все экземпляры и закройте другие соединения с обеими БД. Флаг не обнаруживает восстановление автоматически и не ограничивает прямой доступ к БД; оставляйте его включённым, пока полнота auth не подтверждена и сверка не завершена.

## Индекс публикаций

Миграция `005` добавляет outbox: в индекс передаётся только заголовок опубликованного публичного материала, при скрытии или удалении создаётся tombstone. События фиксируются в той же транзакции, что и изменение публикации. Индекс содержит только кандидатов: проверка текущих прав через auth/user перед выдачей результатов ещё не реализована, поэтому внешний поиск публикаций не включён.

Издатель запускается отдельно из `backend` командой `go run ./content/cmd/search-publisher -config ../config.toml`. Ему требуются PostgreSQL 15 или новее, отдельная роль БД и отдельный ключ записи `content_writer_secret` search. Пример для отдельного защищённого файла конфигурации издателя:

```toml
[services.content.search]
url = "http://127.0.0.1:8085"
writer_secret = "ОТДЕЛЬНЫЙ_КЛЮЧ_CONTENT_ИЗ_SEARCH"
database_user = "content_search_publisher"
database_password = "ЗАМЕНИТЬ"
```

Роли издателя дайте `USAGE` на схему, `SELECT` и `DELETE` на `content_search_events`, а также `UPDATE` только колонок `lease_token` и `lease_until`. Ролям приложения и очистки не разрешайте менять outbox; никто из этих процессов не должен владеть схемой, функцией или таблицами, иметь `CREATE` в `public`, `BYPASSRLS`, `SET session_replication_role` или быть суперпользователем. Эти ограничения и включённые триггеры проверяются при запуске. Секрет, пароль роли и доступ к конфигу ограничьте процессом издателя. Текущий канал к search поддерживает только loopback; для разных серверов нужны mTLS и проверка идентичности.

При отказе search событие сохраняется и повторяется после истечения аренды. При восстановлении content или search остановите **все** экземпляры издателя и включите `recovery_mode` в его конфигурации до сверки: уже запущенный процесс не перечитывает конфигурацию. Автоматической защиты от отката источника и полной процедуры восстановления индекса публикаций пока нет; риск и ограничения — в `BUGS.md`.

Внутренний `POST /internal/search/recheck` с `X-Internal-Secret` и JSON `{"query":"...","ids":["UUID"]}` возвращает совпадающие актуальные публичные публикации в порядке кандидатов. Метод ограничен 50 ID и не является проверкой сессии или активности автора; эти проверки выполняет user через auth.

Миграция `006` добавляет замену вложений приватного черновика. Приложению требуется `EXECUTE` на `public.content_set_draft_media(uuid,uuid,bigint,uuid[])`. Прямые права записи в `content_post_media` по-прежнему запрещены, роль очистки команду не выполняет.

Внутренний `PUT /internal/drafts/{id}/media` принимает `{"revision":1,"media_ids":["UUID"]}` и возвращает текущую ревизию. Порядок сохраняется, допускается до 16 уникальных ID. Пустой список отсоединяет файлы. Действуют обычные внутренний секрет и cookie. Content перепроверяет в user, что каждый файл готов и принадлежит автору. Черновики возвращают `media_ids` внутри `GET /internal/drafts`. Отзыв между проверкой и сохранением может оставить устаревшую ссылку в приватном черновике. При публикации состояние, тип и право на каждый файл нужно проверить снова.

Внутренний `POST /internal/drafts/{id}/publish` принимает `{"revision":2,"visibility":"public"}`. По умолчанию видимость `private`. Перед записью content проверяет заголовок, готовность, владельца и тип всех вложений. Повтор с той же исходной ревизией и видимостью переиспользует переход, пока вложения остаются доступными. Public создаёт событие для поискового индекса. `GET /internal/posts/{id}` возвращает приватную публикацию только автору, а публичную также активному вошедшему зрителю после проверки обоих аккаунтов в user/auth. Для обоих методов нужны внутренний секрет и сессия.

Кабинет автора может проверять файл отдельно. При просмотре публикации media вызывает user с ID публикации, а user проверяет конкретную привязку через `GET /internal/posts/{id}/media/{media}/access`. Content проверяет, что публикация ещё доступна зрителю и что владелец файла совпадает с её автором. Готовность файла и актуальность сессии проверяет user. Публичный режим сейчас требует действующую сессию. Доступ стороннего зрителя к платным публикациям появится после подключения прав покупки.

Для миграции `009` добавьте роли приложения `EXECUTE` на `public.content_publish_post(uuid,uuid,bigint,text)`. Роли очистки исполнение запрещено. Старый `public.content_publish_private(uuid,uuid,bigint)` оставлен для предыдущего бинарника. После его выключения можно отозвать прежний GRANT. Подключите описанный в user внутренний клиент content до публикации общедоступных материалов.

Внутренние `POST /internal/posts/{id}/remove` и `POST /internal/posts/{id}/restore` принимают `{"revision":2}` и возвращают новую ревизию. Для удаления из публичной выдачи транзакция записывает tombstone поиска. Восстановление возможно для записи, удалённой автором, и переводит её в приватный черновик. При публикации вложения перепроверяются. Повтор удаления с исходной ревизией безопасен, а повтор восстановления с устаревшей ревизией возвращает 409. Для миграции `008` добавьте роли приложения `EXECUTE` на `public.content_change_author_removal(uuid,uuid,bigint,boolean)`. Прямая запись в `author_removed_at` запрещена. Вложения остаются привязанными.

### Лайки и избранное

`PUT /internal/posts/{id}/like` и `PUT /internal/posts/{id}/favorite` добавляют реакцию, `DELETE` на том же маршруте снимает её. Запрос без тела требует внутренний секрет и сессию. Успешный повтор возвращает 204. Сервис проверяет в user/auth зрителя и автора, затем в транзакции сверяет, что публикация остаётся доступной. В данных публикации `likes` — число лайков, `liked` и `favorited` — признаки текущего зрителя.

Миграция `010` добавляет таблицы `content_post_likes`, `content_post_favorites` и `content_post_statistics`. Роли приложения нужны `SELECT` на них и `EXECUTE` на `public.content_set_reaction(uuid,uuid,uuid,text,boolean)`. Роли очистки нужен только `EXECUTE` на `public.content_purge_viewer_reactions(uuid)` в дополнение к прежним правам. Ни одной из этих ролей не давайте прямую запись в новые таблицы. При очистке аккаунта сервис удаляет лайки и избранное порциями, пересчитывает счётчики и продолжает существующее удаление публикаций. Окончательное удаление поста каскадно очищает его реакции.

`GET /internal/favorites?limit=20` возвращает закладки текущей сессии по времени добавления. `limit` от 1 до 40. Content проверяет текущую видимость поста и перед ответом одним запросом к user перепроверяет авторов. Если присутствует `next_cursor`, передайте его как `cursor`, даже если текущая страница пуста. Курсор зашифрован и привязан к владельцу списка.

### Просмотры

Миграция `011` добавляет счётчик `views` в данные публикации. Media отправляет событие после начала фактической выдачи файла. Content повторно проверяет привязку и текущую публичность поста и засчитывает одному зрителю один просмотр публикации за сутки UTC. Авторские просмотры исключаются. Запоздалое событие за вчера принимается, пока более свежий день для этой пары ещё не записан. Периодическая очистка удаляет просроченные записи дедупликации, а очистка аккаунта удаляет их по зрителю. Общие счётчики сохраняются без идентификаторов зрителей.

Укажите в `[services.content].media_view_secret` новый случайный секрет, совпадающий с `[services.media.views].secret`. Роли приложения нужны `EXECUTE` на `public.content_count_post_view(uuid,uuid,uuid,integer)` и `public.content_prune_view_receipts()`, роли очистки — `EXECUTE` на `public.content_purge_view_receipts(uuid)`. Обе роли работают без прямого доступа к таблице дедупликации.

Для автоматического качества примените миграцию 012 и выдайте роли приложения `EXECUTE` на `public.content_popular_for_playback(uuid)`. Порог популярности составляет 100 разных учтённых зрителей с начала текущего дня UTC. При проверке вложения content передаёт решение через user в media.

### Поиск после восстановления базы публикаций

Изолируйте восстановленные базы от клиентов и остановите content, его издатель поисковых событий, search и всех остальных писателей индекса. Проверьте актуальность резервной копии и согласуйте удалённых авторов. Из каталога `backend` выполните `go run ./content/cmd/search-rebuild -config ../config.toml -isolated`. Для доступа используются настройки баз content и search, включая отдельные migration_user и migration_password при наличии.

Команда под блокировкой заново ставит публичные публикации в очередь, пропускает авторов в процессе удаления, повышает границу версий индекса content и очищает его старые документы. Индекс пользователей сохраняется. При ошибке между фиксациями оставьте сервисы изолированными и повторите команду. После успеха запустите search и content search-publisher, дождитесь опустошения content_search_events и проверьте результаты по известным публичным и удалённым публикациям перед открытием трафика.

### Комментарии

Примените миграцию 013. Роли HTTP-приложения нужны SELECT на content_comments и EXECUTE на content_write_comment(uuid,uuid,uuid,text). Роли очистки нужен EXECUTE на content_purge_comments(uuid). Записи изменяются функциями с проверкой состояния публикации и владельца комментария.

- `PUT /internal/posts/{id}/comments/{comment}` принимает JSON с полем `body` длиной до 2000 символов. Клиент генерирует UUID комментария до отправки. Создание возвращает 201, точный повтор — 204, изменение текста по тому же ID — 409. Начальный лимит составляет пять новых комментариев за минуту на автора.
- `GET /internal/posts/{id}/comments?limit=20&cursor=…` возвращает `comments` от новых к старым и необязательный `next_cursor`. Курсор привязан к публикации и зрителю. При фильтрации недоступных авторов страница может содержать меньше элементов, чем указанный лимит.
- `DELETE /internal/posts/{id}/comments/{comment}` позволяет автору убрать свой текст и возвращает 204 при повторе. Удалённый ID сохраняется до очистки аккаунта или публикации, поэтому повтор старого PUT не возвращает комментарий.

Маршруты требуют внутренний секрет content и cookie действующей сессии. Текст комментария предназначен для отображения обычным текстом.

### Тестовые покупки отдельных публикаций

По умолчанию продажи выключены. Для испытаний используйте отдельную БД content и отдельную роль. Укажите `test_sales = true` в `[services.content]`. Автор сначала публикует пост с видимостью private и затем создаёт предложение на конкретную редакцию. Предложение доступно покупателю по ID поста. До покупки ответ содержит автора, редакцию, цену и валюту. Ссылки на вложения выдаются после обычных проверок user и content.

| Запрос | Результат |
| --- | --- |
| PUT /internal/test-sales/posts/{id}/offer | Автор передаёт revision, amount_minor и currency. Поддерживаются RUB, USD и EUR. Повтор с прежними данными возвращает 204. |
| GET /internal/test-sales/posts/{id}/offer | Текущие условия покупки. |
| PUT /internal/test-sales/posts/{id}/orders/{request_id} | Покупатель передаёт revision предложения и собственный UUID операции в пути. Первое подтверждение возвращает 201, точный повтор — 200. |
| GET /internal/test-sales/orders/{request_id} | Покупатель получает свою тестовую квитанцию и время отзыва, если доступ отозван. |

Денежные суммы задаются в минимальных единицах валюты. Успешные ответы с данными содержат `mode: "test"`. Отзыв закрывает последующие запросы к закрытой публикации и вложениям. При снятии и повторной публикации создаётся другая редакция, требующая собственного предложения. Изменение суммы для уже предложенной редакции возвращает 409.

Обычный режим требует, чтобы роль HTTP не могла читать даже отдельные колонки `content_test_offers`; неверные разрешения блокируют запуск.

История заказов принимает `limit` от 1 до 40, по умолчанию 20. Для следующей страницы передайте `data.next_cursor` как `cursor`. Порядок идёт по убыванию времени подтверждения, при совпадении времени — по убыванию UUID заказа. Курсор закреплён за покупателем. История показывает исходные суммы, валюту и время отмены, если заказ отозван. Текущая доступность публикации проверяется при открытии поста.

Перед обновлением content примените миграцию `032_test_order_history.sql` во всех БД content. Выдайте `EXECUTE` для `content_test_receipts(uuid,timestamptz,uuid,integer)` только роли тестового режима.

Перед запуском примените миграции 014 и 015. Обоим HTTP-режимам выдайте EXECUTE на content_test_entitled(uuid,bigint,uuid). Только тестовой роли предоставьте SELECT на content_test_offers и EXECUTE на content_test_offer, content_test_purchase, content_test_receipt, content_test_revoke и перегрузки content_set_reaction, content_write_comment и content_count_post_view с дополнительным флагом boolean. Обычные функции реакций, комментариев и просмотров по-прежнему нужны HTTP-ролям. Роли очистки требуется EXECUTE на content_purge_test_orders(uuid). Прямое изменение таблиц продаж прикладными ролями и чтение таблицы заказов при запуске отклоняются.

### Собственные рекламные кампании

Примените миграции content 016 и 033 и auth 020. Роли HTTP приложения выдайте EXECUTE для `content_select_ad(uuid,uuid,text)`, `content_ad_campaign_list(uuid,integer)` и `content_ad_campaign_put(uuid,uuid,bigint,text,text,text,timestamptz,timestamptz,boolean,bigint)`. Роли очистки нужен EXECUTE для `content_purge_ad_deliveries(uuid)`. Роль `ad_operator` назначает доверенный администратор БД auth. После изменения роли нужно войти заново.

- `GET /internal/ads/campaigns` возвращает `campaigns` и необязательный `next_cursor`. Принимает `limit` от 1 до 40 (по умолчанию 20) и `cursor`.
- `PUT /internal/ads/campaigns/{id}` принимает `revision`, `placement`, `headline`, `destination`, `starts_at`, `ends_at`, `enabled` и `delivery_budget`. Для создания передайте `revision: 0`, для правки — текущую редакцию. Первая запись возвращает 201, правка и точный повтор — 204. Конфликт редакции или бюджет меньше уже выданного объёма возвращают 409. Для паузы установите `enabled: false`. Функция БД пишет в журнал одну запись на изменённую редакцию.

Оператор задаёт одну из лент `mixed_feed`, `photo_feed`, `video_feed` для показа и перехода. Клиент отображает заголовок обычным текстом и строит ссылку по идентификатору ленты.

`PUT /internal/ads/{placement}/{request_id}` с пустым телом, внутренним секретом и действующей сессией возвращает `campaign_id`, `headline` и `destination`. Если подходящей кампании сейчас нет, возвращается 204. Совпадающий UUID успешной операции даёт тот же результат, пока кампания активна в исходной ленте, без повторного списания лимита. Для того же UUID с другим местом показа вернётся 409.

У каждого зрителя может быть одна новая выдача конкретной кампании и до трёх выдач суммарно за скользящий час. При параллельных запросах лимит кампании защищён блокировкой строки PostgreSQL. Список кампаний показывает `deliveries`, `delivery_budget` и `reported_impressions`.

`PUT /internal/ads/impressions/{request_id}` принимает пустое тело, внутренний секрет и действующую сессию. Клиент отправляет UUID исходной выдачи после двух секунд видимости объявления. Сервер принимает первое сообщение от того же зрителя через 2 секунды после выдачи и до истечения 2 минут. Успех и повтор возвращают 204, преждевременный запрос — 409, просроченный — 410. Чужая выдача и потеря доступности кампании возвращают 404. Метрика отражает сообщения браузера о показах. Для расчётов и начисления баллов нужен отдельно проверяемый источник. Перед обновлением примените миграцию content 034 и выдайте роли HTTP `EXECUTE` для `content_report_ad_impression(uuid,uuid)`.

### История публикации

Миграция 017 создаёт исходное событие snapshot для каждой существующей публикации. Последующие события записываются в той же транзакции, что и изменение состояния. Создание, публикация, снятие автором и возврат в черновик имеют отдельные типы событий. Обычная правка текста или вложений может пропустить номер редакции в истории. Сведения до миграции ограничены исходным снимком.

`GET /internal/posts/{id}/history` после миграции 040 возвращает до 20 событий, включая `moderation_hidden` и `moderation_unhidden`. Скрытие сохраняет редакцию публикации, поэтому для упорядочивания событий одной редакции используется `event_id`. Если есть поле `next`, передайте его целиком в параметре `before` следующего запроса. Миграция обновляет индекс истории и фиксирует новые события скрытия с момента применения. Маршрут доступен только владельцу с действующей сессией и внутренним секретом. При окончательном удалении публикации её история удаляется каскадно. Роли HTTP нужен SELECT на content_post_history. Триггер записывает события без прав прямой записи у HTTP-роли.

### Жалобы на публикации и комментарии

Примените миграцию 018. Роли HTTP нужны EXECUTE для content_submit_report(uuid,uuid,uuid,uuid,text,boolean) и content_own_report(uuid,uuid). Роли очистки нужен EXECUTE для content_purge_reporter(uuid). Отдельные права на таблицу жалоб этим ролям не требуются.

`PUT /internal/reports/{id}` принимает UUID запроса в пути и JSON с post_id, необязательным comment_id и reason. Допустимые причины — spam, harassment, consent, age_safety, other. Маршрут требует внутренний секрет и действующую сессию, а новая жалоба требует доступ к цели. Первая отправка возвращает 201, совпадающий повтор — 204, другая жалоба того же заявителя на ту же цель — 409. После пяти новых жалоб за скользящий час возвращается 429.

`GET /internal/reports/{id}` возвращает цель, причину, время и статус жалобы только её заявителю. При создании статус pending. Обработка решений модераторов подключается отдельно.

### Обложка видео

После миграции 019 автор может вызвать `PUT /internal/posts/{id}/cover` для черновика или опубликованного видео. JSON содержит текущую revision и media_id готового фото того же владельца. Передайте null в media_id, чтобы вернуть автоматическую обложку. Маршрут возвращает 204 или 409, если редакция публикации изменилась. Смена обложки сама по себе не меняет редакцию ролика. После миграции 042 можно передать `frame` со значением `poster-25.jpg` или `poster-60.jpg` и `media_id` первого видео во вложениях. Выбирайте значение из `cover_frames` в статусе загрузки. Для выбора кадра настройте `[services.content.media]` с loopback-адресом Rust media и его `internal_secret`. Content проверяет JPEG запросом HEAD по маршруту владельца перед сохранением. Если кадра нет или доступ отозван, выбор не сохраняется. До обновления content дайте HTTP-роли `EXECUTE` на `content_set_video_cover(uuid,uuid,bigint,uuid,text)`. Старый вызов сохранён для прежних экземпляров.

Ленты, избранное, поиск и карточка возвращают cover_media_id. Запрашивайте его через `GET /internal/posts/{post}/cover/{media}/preview` в media. Маршрут отдаёт выбранный кадр, уменьшенную копию выбранного фото или автоматическую обложку первого вложения. Если выбранный JPEG отсутствует, media пробует автоматическую обложку. User и content проверяют текущее право доступа, привязку, готовность и отзыв файла. При отзыве выбранного фото этот адрес возвращает 404, а автор может выбрать другое фото или вернуть автоматическую обложку.

Роли HTTP нужны SELECT на content_video_covers и EXECUTE для content_set_video_cover(uuid,uuid,bigint,uuid). При физическом удалении поста привязка удаляется каскадно.

### Очередь модерации

После миграции 038 `GET /internal/moderation/cases` возвращает до 50 доступных случаев. Для следующей страницы передайте `next_cursor` как `cursor`. Если `next_cursor` отсутствует, последняя страница достигнута. В первую очередь идут дела с повышенным приоритетом, затем действует сортировка по дате создания и ID. С миграции 045 жалобы на возраст и согласие получают высокий приоритет при подаче. Модератор может один раз вернуть такое дело в очередь через явную эскалацию. Очередь обновляется между запросами, поэтому дело, получившее более высокий приоритет после загрузки страницы, может появиться после обновления списка с начала. До обновления content выдайте HTTP-роли `EXECUTE` на `content_moderation_queue(uuid,boolean,timestamptz,uuid)`. Прежняя функция сохранена для старых экземпляров. Ответ содержит ID случая и объекта, причину и редакцию. Личность заявителя в ответ не включается. Доступ проверяется по действующей сессии и роли moderator в auth через user. Собственные жалобы и материалы исключаются.

После миграции 037 `GET /internal/moderation/cases/{id}` возвращает карточку назначенному модератору и до 50 событий, начиная с последних. Если `next_before_revision` содержит число, передайте его как `before_revision` в следующем запросе. Значение `null` означает конец журнала. Во время действующего назначения карточка содержит текст публикации или жалуемого комментария, включая скрытый текст. После закрытия дела назначенному модератору доступны метаданные и журнал. Миграция 039 ограничивает просмотр текста и скрытие поста редакцией публикации, на которую поступила жалоба. До обновления content выдайте его HTTP-роли `EXECUTE` на `content_moderation_case_detail(uuid,uuid,bigint)`. Двухаргументная функция сохранена для прежних экземпляров content.

Миграция 036 добавляет `media_ids` для рассматриваемой жалобы на пост. Для HTTP-роли нужен `EXECUTE` на `content_case_media_access(uuid,uuid,uuid,uuid)`. Выдача требует действующего назначения и привязки файла к публикации, существовавшей на момент жалобы. Для жалобы на отдельный комментарий карточка показывает текст комментария.

`PUT /internal/moderation/cases/{id}` принимает request_id, revision и action. Действие claim назначает случай текущему модератору на 24 часа. Release возвращает в очередь, escalate возвращает с повышенным приоритетом. Dismiss отклоняет жалобу. Confirm подтверждает и требует rule из списка причин и severity со значением low, medium, high или critical. Ответ содержит следующую редакцию. Совпадающий повтор возвращает прежний результат, конфликт редакций или назначения — 409. Действия и решения записываются в журнал. Подтверждение применяет санкцию по действующей политике. После миграции 044 действие `remove` принимает те же поля rule и severity и одновременно снимает материал с выдачи. Дело закрывается со списанием баллов один раз. При отмене решения по апелляции видимость восстанавливается с учётом остальных прав доступа. Порядок пересмотра описан ниже.

Для действий по делу HTTP-роли нужен `EXECUTE` на `content_moderate_report(uuid,uuid,uuid,bigint,text,text,text)`. Содержимое очереди и журнал защищены от прямой записи прикладными ролями.

После миграции 021 назначенный модератор может выполнить действие hide. Оно временно скрывает публикацию или комментарий. Скрытая публикация исчезает из ленты и из повторной проверки поиска, а проверка доступа к её медиа возвращает отказ. Действие dismiss снимает скрытие, поставленное этим случаем. Confirm сохраняет скрытие. Редакция публикации при скрытии не меняется, поэтому после отклонения жалобы ранее выданное право на эту редакцию снова действует. Обжалование подтверждённого решения остаётся в плане.

После миграции 022 окончательная очистка заявителя удаляет его UUID и идентификатор запроса из случаев, по которым модератор уже действовал, и из жалоб о согласии или возрасте. Эти случаи остаются доступны модераторам, уже применённое скрытие сохраняется. Обычные необработанные жалобы удаляются. Офлайн-сверка использует ту же процедуру через роль миграций. Старые очистки, выполненные до обновления, могут потребовать отдельной сверки оставшихся скрытий.

### Уведомления о модерации и апелляции

После миграции 023 `GET /internal/me/moderation/notices` показывает владельцу до 50 недавних решений об его публикациях и комментариях. В ответ входят причина, тяжесть, текущее скрытие и результат апелляции при наличии. `PUT /internal/me/moderation/appeals/{id}` принимает ID случая и JSON со statement до 1000 символов. Подтверждённое решение можно обжаловать один раз. Первая отправка возвращает 201, точный повтор — 204.

Для модератора `GET /internal/moderation/appeals` возвращает до 50 ожидающих апелляций, а `PUT /internal/moderation/appeals/{id}` принимает outcome со значением upheld или reversed. Если модератор участвовал в исходном решении, его сессия не даёт права на пересмотр. Reversed снимает скрытие, применённое этим случаем. Пост и права на его редакцию восстанавливаются при сохранении остальных условий доступа.

Роли HTTP выдайте EXECUTE для content_owner_moderation(uuid), content_submit_appeal(uuid,uuid,text), content_appeal_queue(uuid) и content_review_appeal(uuid,uuid,text). Обычные уведомления запрашиваются из профиля. После миграции 024 удовлетворённая апелляция возвращает баллы, списанные именно по этому случаю.

Миграция 047 добавляет `GET /internal/moderation/appeals/{id}` для независимого модератора. Пока апелляция открыта, маршрут возвращает заявление, решение и применимый текст. Для HTTP-роли нужен `EXECUTE` на `content_appeal_detail(uuid,uuid)`. С миграции 048 карточка жалобы на пост содержит `media_ids`. Независимый модератор может открыть эти вложения по существующему адресу media для дела, пока апелляция открыта. Для жалобы на комментарий возвращается текст без вложений поста.

### Баллы за модерацию

Миграция 024 добавляет версионируемую политику и журнал начислений. Первая политика задаёт 100 начальных и максимальных баллов. Списание зависит от причины и тяжести. Настраиваемые значения хранятся в content_points_policies и content_points_deductions. При смене политики оператор подготавливает полный набор правил в новой версии и переключает активную версию одной транзакцией. Порог и максимум уже заведённого счёта продолжают рассчитываться по его исходным значениям.

Подтверждение нарушения и запись списания происходят в одной транзакции. При остатке 30% начальных баллов или меньше создание новых комментариев возвращает 403. Удаление своего комментария и точный повтор создания остаются доступны. Решения, вынесенные до установки миграции, не списывают баллы задним числом.

`GET /internal/me/moderation/points` возвращает баланс, исходные и максимальные баллы и признак ограничения комментариев. Роли HTTP нужен EXECUTE на content_owner_points(uuid), роли очистки — на content_purge_points(uuid). Прикладные роли не получают прямого доступа к таблицам политики и баллов.

Миграция 043 добавляет необязательное восстановление баллов за отчёты о показах, принятые сервером. В действующей политике `daily_ad_points=0` по умолчанию. При значении 1 аккаунт может получить один балл за день UTC после показов разных кампаний, число которых задаёт `ad_campaigns_required` (по умолчанию 3). Повторы, активный бан и максимальный баланс не дают начисления. Запись журнала хранит идентификатор отчёта, после которого начислили балл. Сервер проверяет право, выдачу и временное окно, а видимость рекламы на экране сообщает браузер. Перед включением оцените качество этих событий.

После миграции 025 ответ points включает warnings и, при действующем ограничении, ban. Предупреждения фиксируются один раз на каждом пороге потери 50%, 70%, 80% и 90% начального баланса. Новое достижение нуля создаёт ступень бана при отсутствии действующего бана. Последовательность состоит из 24 часов, семи дней, календарного месяца по UTC и бессрочного бана. При определении ступени учитываются прошлые баны, сохранившиеся после апелляций. Истечение срока само по себе не создаёт новое ограничение. Отмена решения снимает связанный с ним бан.

Роли HTTP нужны EXECUTE для content_owner_point_notices(uuid) и content_active_points_ban(uuid). Content является источником состояния бана. User запрашивает его при проверке доступа к публичным функциям.

В интегрированном развёртывании user должен иметь URL и секрет content. Маршрут `GET /internal/participation/{id}` принимает существующий служебный секрет content и возвращает 204 или 403. При отказе content проверка участия завершается 503. Разворачивайте версии user, content, media и media-processing с этим контрактом вместе. Действующая сессия сохраняет доступ к собственному профилю, баллам, уведомлениям и апелляции.

### Восстановление баллов за просмотры

Миграция 026 по умолчанию возвращает один балл за день UTC при учтённых просмотрах публичных постов трёх разных авторов. Используются серверные события media, прошедшие порог выдачи. Свои публикации, повтор того же просмотра, тестовые покупки и события за предыдущий день не увеличивают прогресс. Лимит действует на аккаунт и общий для всех устройств. При достижении максимума или во время бана начисление пропускается. После истечения временного бана баллы можно восстанавливать с нуля.

Активная политика задаёт daily_activity_points и activity_authors_required. Ноль в первом параметре отключает начисление. Один день может дать только одну запись activity в журнале. Пополнение за рекламу и донаты требует отдельного события.

### Отложенная публикация

Миграция 027 добавляет `PUT /internal/drafts/{id}/schedule`. Автор отправляет `revision`, `visibility` и обязательное поле `publish_at` в RFC 3339 с нулевыми секундами и явным смещением, например `2027-01-20T20:30:00+03:00`. Сервер приводит время к UTC. Явный `null` отменяет задание, новая дата заменяет его, а запрос без поля возвращает 400. Интерфейс определяет смещение по часовому поясу на выбранную дату. Если местная минута повторяется при переводе часов, интерфейс даёт выбрать один из двух моментов. Если выбранной минуты не существует, интерфейс просит выбрать другую. GET /internal/drafts возвращает `publish_at` и `planned_visibility`. Правка черновика сбрасывает расписание.

Content подбирает задания после указанной минуты и хранит следующую попытку в PostgreSQL. Обработчик сверяет активность автора и готовность всех вложений через user, затем повторно проверяет актуальность задания, редакцию, скрытие и бан перед публикацией. При недоступности сервиса или неготовом вложении попытка повторяется. Снятые и отредактированные черновики не могут быть опубликованы старым заданием.

Выдайте роли HTTP SELECT на content_scheduled_posts и EXECUTE для content_schedule_post(uuid,uuid,bigint,timestamptz,text), content_claim_scheduled_post() и content_publish_scheduled_post(uuid,uuid,uuid,bigint). Режим восстановления останавливает публикацию по расписанию.

На одном сервере существующий HTTP-режим использует loopback и внутренний секрет content. Для связи с удалённым user задайте HTTPS-адрес `services.content.user.url`, совпадающий с SAN сертификата user, и пути `peer_ca_file`, `peer_cert_file` и `peer_key_file` в `[services.content.user.tls]`. В `[services.user.content]` укажите `client_uri`, совпадающий с URI SAN клиентского сертификата content и отличный от идентичностей auth и media-processing. CA клиентского сертификата content должен входить в `services.user.tls.client_ca_file`. Задайте одинаковый отдельный `publication_secret` в `[services.content.user]` и `[services.user.content]`. Сертификат content даёт доступ к этой служебной проверке при предъявлении секрета. Обратные вызовы из user в content настраиваются отдельно.

### Мои публикации

`GET /internal/me/posts` показывает владельцу черновики, запланированные, опубликованные, снятые и скрытые материалы. Запрос принимает limit от 1 до 40, cursor из next_cursor и необязательный state со значением draft, scheduled, published, removed или hidden. Курсор привязан к аккаунту и фильтру. Список показывает название, тип, видимость, редакцию и время публикации или расписания при наличии. Status хранит состояние публикации, state дополнительно отражает запланированный или скрытый материал.

Запрос требует внутренний секрет и действующую сессию владельца. Список остаётся доступен во время ограничения участия. Скрытие материала по-прежнему блокирует выдачу файлов. Индекс для списка добавляется миграцией 028.

### Редактирование опубликованного текста

`PUT /internal/posts/{id}` принимает revision, title и description по той же схеме, что `PUT /internal/drafts/{id}`. Изменение доступно владельцу опубликованного и видимого поста. Ответ содержит текущую редакцию после правки. Точный повтор возвращает тот же результат, конфликт редакций возвращает 409. Изменение публичного заголовка обновляет поисковый индекс через outbox.

Для формы редактирования используйте revision из карточки. Для создания тестового предложения используйте published_edition. Правка текста сохраняет эту редакцию файлов и выданный на неё доступ. После снятия и новой публикации создаётся другая редакция файлов.

После миграции 029 выдать HTTP-роли EXECUTE для content_edit_post(uuid,uuid,bigint,text,text,text) и отозвать UPDATE на title, description и revision таблицы content_posts. Права INSERT на колонки черновика сохраняются. Роли очистки исполнение функции не предоставляется.

### Короткие и длинные видео

Миграция 030 сохраняет длительность первого видео при ручной и отложенной публикации. Обложка не влияет на это значение. Лента возвращает duration_ms. Параметр length=short выбирает ролики до 60 секунд включительно, length=long — более длинные. Старые публикации без длительности видны в общей видеоленте. При фильтре длины они пропускаются.

Роли HTTP нужны EXECUTE для content_publish_post_duration(uuid,uuid,bigint,text,bigint) и content_publish_scheduled_post(uuid,uuid,uuid,bigint). Для плавного обновления сохранены старые функции, которые принимают публикацию без длительности.

### Рекомендации

Миграция 031 добавляет снимки рекомендаций. Первый запрос за час создаёт снимок для не более чем 1000 самых свежих публичных публикаций за 30 дней. Учитываются просмотры за текущий и предыдущий день UTC. Сначала сортируются лучшие публикации разных авторов, затем вторые и последующие. Фильтры фото, видео и длительности работают поверх того же снимка. При каждом запросе сверяются текущее скрытие, видимость и автор. Курсор продолжает тот же снимок после удаления отдельной публикации. Снимки старше 24 часов удаляются при подготовке следующего.

Карточки хронологической ленты и рекомендаций возвращают `likes`, `views`, `liked` и `favorited`. User передаёт идентификатор проверенной сессии в служебном `X-Viewer-ID`. Публичные счётчики одинаковы для всех зрителей, признаки реакции и закладки вычисляются для текущего аккаунта.

Роли HTTP выдайте SELECT на content_recommendations и EXECUTE для content_ensure_recommendations(). Роли очистки дополнительных прав не нужны. Запись снимка выполняется функцией с ограничёнными полномочиями вызывающей роли.

Миграция 050 добавляет внутренний `POST /internal/safety-reports`. JSON содержит `post_id` и `reason` (consent или age_safety). Доверенный вызывающий компонент передаёт внутренний секрет. Запрос не требует сессии и получает одинаковый 202 для неизвестного, закрытого или уже заявленного поста и для новой жалобы. Закрытый пост не добавляется в очередь. Общий аварийный лимит 120 запросов за час UTC даёт 429. При выводе формы во внешний API требуется отдельное ограничение на входе. Роли HTTP добавьте EXECUTE на `content_submit_anonymous_safety_report(uuid,text)`.

С миграции 051 оператор может получить отчёт кампании по `GET /internal/ads/campaigns/{id}/report?start=YYYY-MM-DD&end=YYYY-MM-DD`. Конечная дата исключается, максимум 31 день UTC. Дни без событий возвращаются с нулями. Выдачи и принятые отчёты о показе относятся к дате самого события. Дневная статистика начинается с применения миграции. HTTP-роли нужен EXECUTE на `content_ad_campaign_daily_report(uuid,date,date)`.
