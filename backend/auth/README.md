# Auth

Для сборки требуется Go 1.26 или новее; в эксплуатации используй актуальный поддерживаемый патч Go.

Auth предоставляет вход по логину или email и паролю, серверные сессии, просмотр устройств и отзыв сессий. Пароли хранятся как Argon2id с уникальной солью, случайные токены сессии — только в виде SHA-256 хеша. Веб-клиент получает `HttpOnly`, `SameSite=Strict` cookie; по умолчанию она также `Secure`. Для POST требуется `Origin`, совпадающий с `[http].allowed_origin`.

## API

- `POST /api/auth/login`: JSON `identifier`, `password`, `device_name`; необязательный `recovery_token` — одноразовый токен из письма восстановления пароля. Если лимит аккаунта исчерпан, владелец с подтверждённой почтой может запросить письмо и войти с этим токеном и действующим паролем. Токен расходуется при создании сессии; пароль не меняется. Ограничение по IP сохраняется. Клиенту нужно отдельно реализовать этот сценарий.
- `POST /api/auth/register`: JSON `login`, `email`, `nickname`; ответ `202` не подтверждает, что адрес свободен. Регистрация требует настроенного SMTP.
- `POST /api/auth/register/resend`: JSON `email`; повторяет отправку письма для неподтверждённой регистрации без продления её 24-часового срока. Новая ссылка отменяет предыдущую; ответ `202` одинаков для подходящих и неизвестных адресов.
- `POST /api/auth/confirm-email`: JSON `token`, `password`; пользователь выбирает пароль после получения письма. После ответа `202` профиль создаётся фоновым обработчиком, и вход становится доступен после его успешного завершения.
- `POST /api/auth/password-reset/request`: JSON `email`; ответ `202` одинаков для существующих и неизвестных адресов.
- `POST /api/auth/password-reset/confirm`: JSON `token`, `password`; после восстановления все сессии отзываются, требуется новый вход.
- `POST /api/auth/verify-email/request`: действующая сессия и JSON `password`; отправляет письмо для подтверждения почты ранее созданного аккаунта.
- `POST /api/auth/verify-email/confirm`: JSON `token` из письма; после подтверждения для старого аккаунта доступно восстановление пароля через почту.
- `POST /api/auth/account/delete`: действующая сессия и JSON `password`; аккаунт сразу отключается, сессии отзываются, архивирование профиля выполняется в фоне.
- `POST /api/auth/account/restore`: JSON `identifier`, `password`; владелец может запросить восстановление в течение 14 дней после удаления.
- `POST /api/auth/moderation/users/{id}/restore`: сессия модератора и JSON с его `password`; восстановление возможно в течение двух календарных месяцев после удаления. Роли по умолчанию никому не назначены; назначение выполняется доверенным администратором БД в `account_roles`, публичного API назначения нет. При изменении роли все сессии затронутого пользователя отзываются, и требуется войти заново; проверенный до изменения пароль нельзя использовать для создания новой сессии. Результат операции записывается в `account_moderation_events` и удаляется при окончательной очистке целевого аккаунта.
- `GET /api/auth/sessions?offset=0`: активные сессии, `online`, `is_current`, `last_seen_at`; до 100 результатов за страницу, `has_more` обозначает следующую страницу.
- `POST /api/auth/heartbeat`: подтверждение активности сессии.
- `POST /api/auth/password`: JSON `current_password`, `new_password`. Смена требует текущую сессию и пароль; остальные сессии отзываются, токен текущей сессии заменяется. Клиент должен сохранить новую cookie из ответа.
- `POST /api/auth/sessions/{id}/revoke`, `POST /api/auth/sessions/revoke-others`, `POST /api/auth/logout`.
- `GET /health`: состояние соединения с БД.
- `GET /ready`: проверка своей БД и защищённого внутреннего соединения с user; возвращает `503`, если зависимость недоступна или настройки связи неверны.

### Ответы и ошибки

Успешный вход возвращает `204 No Content` и `Set-Cookie`. Большинство действий над сессией и смена пароля также возвращают `204`; смена пароля выдаёт новую cookie. Регистрация, запросы писем, удаление и восстановление возвращают `202 Accepted`: это принятие запроса, а не гарантия завершения фоновой операции. Подтверждение сброса пароля и адреса старой учётной записи возвращает `204`.

`GET /api/auth/sessions?offset=0` возвращает `200` и JSON вида:

```json
{
  "sessions": [{
    "id": "70ee5c6a-f508-4c81-8f44-bd86fd30a4d6",
    "device_name": "Laptop",
    "created_at": "2026-01-01T12:00:00Z",
    "last_seen_at": "2026-01-01T12:01:00Z",
    "expires_at": "2026-01-31T12:00:00Z",
    "online": true,
    "is_current": true
  }],
  "has_more": false
}
```

`offset` — целое от 0 до 10000; страница содержит не более 100 сессий. Ошибки возвращаются как обычный текст, а не JSON: `400` — некорректный запрос, `401` — отсутствующая/недействительная сессия или неверные данные входа, `403` — запрет операции или Origin, `404` — ресурс не найден, `409` — конфликт состояния, `429` — ограничение попыток, `503` — недоступна зависимость. Конкретные коды зависят от операции; нельзя делать вывод о существовании аккаунта по ответу на запрос регистрации или письма.

Миграция `018` добавляет поколение сессий: для работы auth runtime-роли нужен SELECT на `session_epoch`. При восстановлении отдельная команда может инвалидировать все сессии одной сменой поколения без событий на каждого пользователя. До такой операции останови все экземпляры auth и user и обнови весь код auth: прежние версии не проверяют поколение и могут принять старые токены. После смены поколения откат на прежний код небезопасен. Инструкции и ограничения — в `backend/OPERATIONS.md`.

Максимальная жизнь сессии — 30 дней, неактивной сессии — 7 дней; онлайн означает активность за последние 2 минуты. Отозванные и окончательно истёкшие сессии удаляются фоновыми пакетами; последнее время активности сохраняется отдельно до окончательного удаления аккаунта. Имя устройства задаётся клиентом и не подтверждает его подлинность. Криптографическая привязка устройства не реализована.

Новый пароль должен содержать не менее 15 символов Unicode и занимать не более 1024 байт. Для дополнительной локальной проверки укажи `[services.auth.password].blocklist_path`: файл UTF-8, один пароль на строку, до 64 МиБ и миллиона уникальных строк. Начальный список и его источники находятся в `passwords/`; для корневого `config.toml` относительный путь — `backend/auth/passwords/common-passwords.txt`. Относительные пути разрешаются от каталога конфига. Данные проверяются локально и никуда не передаются. Для origin вне localhost путь обязателен: без него auth не запустится. Начальный список не охватывает все утечки и требует обновления; без файла локальная разработка использует только короткий встроенный список. Существующие пароли проверяются по прежним правилам до их смены.

Настройка `[services.auth.password].normalize_unicode = true` включает NFC для новых паролей и постепенное обновление существующих при успешном входе. До включения на общей БД обнови все экземпляры auth: прежний код не понимает новый формат. Порядок развёртывания и ограничения отката описаны в `passwords/README.md`.

Перед входом и при проверке сессии auth запрашивает существование профиля у user. При недоступности user доступ закрывается с ошибкой. Для удалённых сервисов нужны HTTPS и два разных секрета из `[security]`: `auth_to_user_secret` для вызовов auth → user и `user_to_auth_secret` для user → auth; каждый не короче 32 байт и одинаково настроен в обоих сервисах. При полностью локальных вызовах для совместимости допускается прежний `internal_secret`. Секреты необходимо держать в тайне; внутренние маршруты также нужно ограничивать сетевыми правилами.

Для поэтапной ротации принимающая сторона может одновременно принимать текущий секрет и дополнительный `previous_auth_to_user_secret` или `previous_user_to_auth_secret` для соответствующего направления. Сначала настрой приём старого и нового значений на обоих сервисах, затем переключи отправителей на новые значения, а после проверки удали старые. Используй отдельные конфиги развёртывания для поэтапного обновления; дополнительные секреты должны отличаться от текущих и друг от друга. Сертификаты загружаются при запуске и для их замены требуется перезапуск; CA-файлы могут содержать старый и новый доверенные CA на период перехода.

Удалённая PostgreSQL требует `sslmode = "verify-full"` с подходящим доверенным сертификатом; более слабые режимы допускаются только для loopback.

Для прямого HTTPS укажи `[services.auth.tls].cert_file` и `key_file`. Оба пути должны быть заполнены вместе; если оба пусты, сервис слушает HTTP и защищённый внешний канал должен обеспечиваться инфраструктурой. Клиенты должны доверять сертификату сервера.

Для mTLS внутренних вызовов задай в этом же разделе `client_ca_file` — доверенный CA для входящего сертификата user и `client_uri` — ожидаемый SPIFFE URI в SAN сертификата user; `peer_ca_file` — CA сертификата сервера user; `peer_cert_file` и `peer_key_file` — клиентский сертификат и ключ auth. Аналогично настраивается user, но его `client_uri` должен совпадать с URI сертификата auth. При заданном `client_ca_file` URI обязателен: внутренние маршруты требуют доверенную цепочку, точное совпадение URI и соответствующий межсервисный секрет. Для удалённого peer mTLS обязателен; локально он необязателен. Публичным клиентам сертификат не нужен. CA для peer заменяет системный набор доверенных CA для этого подключения. Автоматическая ротация сертификатов пока не реализована; ограничивай сеть. Для mTLS соединение должно приходить непосредственно на TLS-сокет сервиса: заголовкам прокси с данными сертификата сервис не доверяет.

Ограничитель входа хранит счётчики в PostgreSQL и работает между экземплярами auth. Он использует фактический адрес TCP-соединения, не доверяя клиентским `X-Forwarded-For`: за прокси все клиенты могут разделять один лимит. Доверенную передачу IP нужно настроить при разработке прокси; напрямую доверять этим заголовкам нельзя.

Ключи счётчиков получают через HMAC, чтобы из одной только таблицы было сложнее определить адрес или логин. Для удалённого peer обязателен отдельный `[security].rate_limit_secret` длиной не менее 32 байт; все экземпляры auth должны использовать одинаковое значение. Он не должен совпадать с текущими и предыдущими межсервисными секретами. При локальной разработке без него используется входящий межсервисный секрет; смена этого значения начинает новые окна ограничений. При исчерпании лимита аккаунта владелец может подтвердить доступ к почте одноразовым токеном и войти с паролем. Это не устраняет ограничения по IP и зависимость от доступности почты; защита от массовой блокировки и доверенная передача адреса за прокси требуют дальнейшей работы.

## Пока не готово

Ручное создание записи credentials не является полноценной регистрацией. Нет защищённого механизма привязки сессии к устройству. Ограничители пока используют адрес TCP-соединения и нуждаются в отдельной настройке доверенного IP за будущим прокси. PostgreSQL остаётся источником прав для сессий, Redis используется как необязательный кэш; итоговое ревью ещё впереди. Сервис нельзя считать готовым к публичной эксплуатации до завершения этих задач.

Для новой БД миграции `migrations/000`–`018` применяются командой `go run ./cmd/migrate -config ../../config.toml` из `backend/auth`. Команда сохраняет историю и не принимает вручную созданную схему без неё; порядок и ограничения описаны в `backend/OPERATIONS.md`. Миграции добавляют регистрацию, восстановление, подтверждение почты, жизненный цикл аккаунта и очистку сессий. При миграции `008` почта старых аккаунтов считается неподтверждённой: её можно подтвердить через `verify-email` до восстановления пароля через почту. Начальные миграции рассчитаны на новую PostgreSQL и не переносят существующие данные.

Почта — единственное разрешённое исключение из самостоятельного размещения: можно использовать собственный SMTP-сервер или внешний почтовый сервис с SMTP. Сейчас реализован SMTP, интеграции с почтовыми HTTP API нет.

Для регистрации заполни `[services.auth.registration]`: `smtp_host`, `smtp_port`, `from`, при необходимости `smtp_user` и `smtp_password`, а также `delivery_key` — отдельный случайный 32-байтный ключ в стандартном Base64 (например, сгенерированный командой `openssl rand -base64 32`). SMTP-сервер должен поддерживать STARTTLS с доверенным сертификатом. Для собственного CA можно задать `smtp_ca_file` — PEM-файл до 1 МиБ; относительный путь отсчитывается от конфига. Если путь пуст, используются системные доверенные CA. Имя или IP SMTP-сервера должны совпадать с сертификатом; отключение проверки не поддерживается. При изменении CA перезапусти auth. Все экземпляры auth с одной БД должны уметь расшифровать накопившиеся сообщения. При ротации сначала настрой на всех экземплярах старый `delivery_key` и новый `previous_delivery_key`, затем переключи их на новый `delivery_key` и старый `previous_delivery_key`; после обработки старых сообщений удали предыдущий ключ. Оба ключа должны быть разными. Удаление ключа раньше времени сделает оставшиеся сообщения нечитаемыми. Храни конфиг с секретами вне Git и с ограниченными правами. При полностью пустых настройках регистрация недоступна; частично заполненные настройки запрещают запуск auth.

Письма содержат ссылки на клиентские маршруты `/auth/verify#token=...`, `/auth/verify-email#token=...` и `/auth/reset-password#token=...`. Фронтенд пока не реализован и должен отправить токен на соответствующий endpoint, а при регистрации или восстановлении запросить у владельца новый пароль. Фрагмент ссылки не отправляется серверу при открытии страницы. Регистрация проверена с реальным user и временной БД, а SMTP — отдельно на локальном TLS-сервере; необходимы проверка развёртывания и итоговое ревью.

Поле `credentials.enabled` запрещает вход и использование сессий отключённой учётной записи. При каждом изменении состояния БД атомарно отзывает существующие сессии и обновляет версию учётных данных, поэтому ранее проверенный пароль нельзя использовать для создания новой сессии. Состояние профиля при этом необходимо согласовать с user. Публичных операций отключения и включения пока нет.

Удаление, восстановление и окончательная очистка выполняются согласованным фоновым процессом auth и user с повторяемыми операциями. Ответ `202` означает постановку операции в очередь: во время отказа user она остаётся незавершённой, а аккаунт — отключённым. Владелец может восстановить аккаунт в течение 336 часов; два календарных месяца для модерации рассчитываются в UTC, одинаково на разных серверах. Если восстановление не успело выполниться в установленный срок, операция отклоняется и аккаунт остаётся в архиве. После двух месяцев процесс удаляет профиль, учётные данные и историю сессий; при недоступности сервиса очистка повторяется после восстановления связи.

События безопасности записываются в PostgreSQL outbox и могут отправляться в Kafka; конфигурация, права и ограничения восстановления описаны в `SECURITY_EVENTS.md`. До настройки независимого журнала и сроков удаления эта отправка не гарантирует восстановление после потери сервера.

Внутренний `GET /internal/users/active?id=<UUID>` принимает до 50 идентификаторов и возвращает только включённые аккаунты без активной операции удаления/восстановления. Требуются существующие межсервисный секрет и, при включённом mTLS, идентичность user; endpoint используется user при проверке владельцев медиа и результатов поиска.
