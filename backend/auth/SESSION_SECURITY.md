# Привязка сессии к устройству

Сейчас клиент предъявляет случайную cookie с серверной сессией. Название устройства передаёт клиент: оно помогает пользователю отличать записи, но не подтверждает, что запрос действительно пришёл с прежнего устройства. При краже cookie её можно использовать до отзыва или истечения; адрес IP и User-Agent ненадёжны как доказательство устройства.

- [WebAuthn](https://www.w3.org/TR/webauthn-3/) и passkeys подходят для входа и повторного подтверждения чувствительных действий. Синхронизируемый passkey может работать на нескольких устройствах. Сам по себе WebAuthn не связывает каждую последующую cookie с устройством и не заменяет серверную проверку и отзыв сессии.
- [Device Bound Session Credentials](https://developer.chrome.com/docs/web-platform/device-bound-session-credentials) предусматривает привязку обновления короткоживущих cookie к ключу устройства. Поддержка зависит от браузера и платформы, поэтому перед внедрением нужны проверка актуальной доступности, совместимости и обычный путь входа для остальных клиентов. Не считать это универсальной защитой от выполнения вредоносного кода внутри активного браузера.
- [DPoP, RFC 9449](https://datatracker.ietf.org/doc/html/rfc9449) связывает OAuth access/refresh-токены с ключом клиента и особенно полезен для native с защищённым хранилищем ключей. Он не является готовой заменой существующей cookie-сессии и требует корректных проверок подписи, метода, адреса, времени, одноразовости доказательства и TLS. Потеря ключа не должна лишать пользователя возможности восстановить аккаунт.

При подключении браузера и native сначала определить домен RP, поддержку платформ и сценарии восстановления. Для браузера разумно отдельно рассмотреть passkeys для входа и DBSC как дополнительное усиление сессии; для native — возможности защищённого хранилища и стандартизованный протокол, если будет вводиться OAuth. Во всех вариантах сохраняются список сессий, немедленный отзыв и проверка прав на сервере. Реализации этих механизмов в проекте пока нет.
