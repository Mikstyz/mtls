# User

Для сборки требуется Go 1.26 или новее; в эксплуатации используй актуальный поддерживаемый патч Go.

Профиль содержит ID, ник, время создания и последнюю активность. Миграции рассчитаны на новую PostgreSQL; если старая схема уже применена, нужна отдельная миграция данных.

Миграции `003`–`008` обязательны; `006` создаёт политику доступа к медиа, `007` — транзакционную очередь индексации профилей, `008` — очередь окончательной очистки content. На существующей БД примените их через мигратор перед запуском обновлённого сервиса. Роль приложения нуждается в DML на новых таблицах и USAGE на последовательности `user_search_events_version_seq`; миграции выполняет отдельная роль.

- `GET /api/users/search?q=ник` — поиск активных пользователей с действующей сессией; выдача повторно проверяется по данным user и auth. Доступны только первые 50 кандидатов; профильной приватности кроме видимости присутствия пока нет.
- `GET /api/users/media/{id}/access` — проверка сессии и права на подготовленный файл; возвращает 204, 401, 404 или 503.
- `GET /api/users/media/{id}/posts/{post}/access` — проверка права на готовый файл в конкретной публикации. User проверяет сессию, профиль, владельца, готовность и отзыв, затем перепроверяет актуальные видимость и привязку в content. Для вызова используется существующая пара `[services.user.content].url` и `search_secret`, совпадающий с внутренним секретом content. При недоступности content возвращается 503. Новый файл остаётся приватным вне публикации.
- `GET /api/users/{id}/access` — подтверждение, что у вошедшего зрителя и автора есть активные профили и аккаунты. Возвращает 204 без данных профиля. Используется при чтении публичной публикации.
- `GET /api/users/{id}/profile` — публичные данные профиля (ID и ник) для вошедшего зрителя. Неактивный или отсутствующий автор возвращает 404.
- `GET /api/users/accounts/active?id=UUID&id=UUID` — пакетная проверка до 40 уникальных аккаунтов с действующей сессией. Возвращает только запрошенные ID с активными профилями и аккаунтами. Content использует метод для избранного.
- `GET /api/users/feed?kind=photo&limit=20` — хронологические карточки публикаций. `kind` принимает `photo`, `video` или может быть опущен для смешанной ленты. `author=<UUID>` ограничивает выборку страницей автора. `limit` от 1 до 40. В ответе `posts` содержат ID, автора, тип, заголовок, время и ID первого файла (если он есть). Полные данные публикации выдаёт content. Если есть `next_cursor`, его значение передаётся как `cursor` с теми же `kind` и `author`. Страница иногда пуста при отключённых авторах, переход доступен до исчезновения `next_cursor`. Курсор привязан к зрителю и фильтрам, ротация ключа content требует начать листание заново.
- `GET /api/users/me` — свой профиль.
- `PATCH /api/users/me` — изменение ника, JSON `nickname`.
- `PATCH /api/users/me/privacy` — настройка видимости статуса, JSON `presence_visibility`: `everyone` или `nobody`.
- `POST /api/users/heartbeat` — подтверждение активности.
- `GET /api/users/{id}/presence` — онлайн и время последней активности пользователя.
- `GET /internal/metrics` — агрегированные счётчики запросов и ошибок auth; требует внутреннюю авторизацию и при включённом mTLS — сертификат доверенного peer.
- `GET /health` — состояние подключения к БД.
- `GET /ready` — готовность своей БД и защищённого внутреннего соединения с auth.

Успешный `GET /api/users/me` возвращает `200` и JSON:

```json
{
  "id": "70ee5c6a-f508-4c81-8f44-bd86fd30a4d6",
  "nickname": "alex",
  "created_at": "2026-01-01T12:00:00Z",
  "last_online": null,
  "presence_visibility": "everyone"
}
```

`last_online` может быть `null`. Успешные изменения профиля и heartbeat возвращают `204 No Content`. Видимый статус возвращается как `{"visible":true,"online":false,"last_online":null}`; скрытый от запрашивающего — как `{"visible":false}`. Ошибки — текстовые ответы: `400` для некорректных данных, `401` для отсутствующей или недействительной сессии, `403` для неверного Origin, `404` для отсутствующего профиля и `503` при недоступности зависимости.

Все операции профиля требуют действующей сессии; POST и PATCH дополнительно проверяют `Origin`. User проверяет cookie через auth по защищённому внутреннему каналу и не принимает ID текущего пользователя от клиента. По умолчанию статус виден любому вошедшему пользователю; при `nobody` другим возвращается только `visible: false`, а владелец продолжает видеть свой статус. Настройка сохраняется при удалении и восстановлении профиля.

Для удалённого auth настрой два разных `[security]` секрета `auth_to_user_secret` и `user_to_auth_secret` одинаковыми с конфигом auth. Общий `internal_secret` допускается только для локального peer. В период ротации user может принимать старый и новый `auth_to_user_secret` через дополнительное поле `previous_auth_to_user_secret`. Доступ к внутренним маршрутам дополнительно ограничивается сетевыми правилами. Для удалённой PostgreSQL требуется `sslmode = "verify-full"`.

Прямой HTTPS включается путями к сертификату и приватному ключу в `[services.user.tls].cert_file` и `key_file`; если оба пусты, сервис слушает HTTP. Для mTLS внутренних вызовов `client_ca_file` задаёт CA входящего клиентского сертификата auth, `client_uri` — его ожидаемый SPIFFE URI в SAN, `peer_ca_file` — CA сертификата сервера auth, а `peer_cert_file` и `peer_key_file` — клиентские сертификат и ключ user. Для удалённого peer mTLS обязателен; локально он необязателен. Внутренние вызовы также требуют соответствующий секрет; публичным клиентам сертификат не нужен. Автоматическая ротация сертификатов ещё не реализована. Подробнее — в `backend/auth/README.md`.

Статус берётся из сессий auth: если хотя бы одна неотозванная сессия была активна в последние две минуты, пользователь онлайн. Видимый ответ содержит `visible: true`, `online` и `last_online`. Для устойчивого отображения клиенту следует посылать heartbeat примерно раз в минуту. При потере связи статус устаревает по тайм-ауту; при отзыве последней сессии становится офлайн сразу. Список и активность устройств предоставляет auth.

Удаление и восстановление запускаются через auth: он проверяет владельца или полномочия модератора, отключает учётные данные и отзывает сессии, а user архивирует или восстанавливает профиль по внутренней операции. Повторы операции распознаются по её ID. Окончательная очистка через два календарных месяца также координируется auth; самостоятельную очистку архива user запускать нельзя.

Внутренний `PUT /internal/users/{id}` с `X-Internal-Secret` и JSON `nickname`, `valid_until` создаёт профиль для регистрации. Срок задаётся auth по аренде обработчика и проверяется по часам БД user после блокировки операций с профилем. Повтор с тем же ID и ником безопасен до окончания срока; изменение параметров, истёкший запрос или повтор после удаления профиля возвращает конфликт. Это внутренняя операция, она не подтверждает email и не является публичной регистрацией. Запись о создании удаляется при окончательной очистке архива; задержанный запрос после этого не может заново создать профиль.

## Поиск, медиа и очистка content

Для подключения поиска задайте `services.user.search.url = "http://127.0.0.1:8085"` и разные `reader_secret`/`writer_secret` в `[services.search]`; отдельно их можно переопределить в `[services.user.search]`. Пустой URL отключает интеграцию. Сейчас поддерживается только HTTP на числовом loopback; для разных серверов требуется mTLS. Очередь изменений профиля хранится в `user_search_events`, работает с повтором и арендой, не запускается в recovery mode. Индекс не является источником прав. После отката БД обязательна офлайн-переиндексация по `backend/OPERATIONS.md`; автоматическое обнаружение отката остаётся открытым багом в `BUGS.md`.

Политика `media_permissions` принадлежит user: по умолчанию доступ закрыт и файл не готов; готовый файл доступен владельцу, пользователям с явным grant и, при `public`, другим вошедшим пользователям. Состояние обоих профилей сверяется в user, а владельца и сессии — в auth. Внутреннее создание приватной неготовой записи реализовано; готовность устанавливается через запрос обработчика, пользовательское управление правами в разработке; не предоставляйте недоверенным ролям права записи в эти таблицы. При окончательной очистке аккаунта grants, выданные этому пользователю, удаляются; политики принадлежащих ему файлов сохраняются, пока сами файлы не будут очищены. Отсутствующий профиль владельца закрывает доступ к ним. Уже начатый поток не прерывается при отзыве.

Для окончательной очистки content задайте `services.user.content.url` и отдельный `purge_secret` в `[services.content]`; можно переопределить ключ в `[services.user.content]`. Сейчас допускается только HTTP на loopback. Без настроенного publisher или при отказе content события `content_purge_events` сохраняются и повторяются после восстановления. Очистка остаётся в очереди, пока у автора есть политики файлов, включая непривязанные загрузки; затем content также отказывается удалять публикации со ссылками на медиа до реализации физического удаления.

Внутренний ответ auth для статуса присутствия содержит обязательный признак активности учётной записи. User не выдаёт статус и время неактивного пользователя; ответ старой версии auth без этого признака приводит к 503. При обновлении сначала установите auth, затем user. Проверка не отменяет ответ, уже начавшийся до удаления аккаунта.

`GET /api/users/search/content?q=...` требует действующую сессию и возвращает публичные публикации с `id`, `author_id`, `kind` и `title`. Search даёт кандидатов, content перепроверяет текущее состояние и заголовок, user проверяет существование профиля, auth — активность автора. При недоступности зависимости возвращается 503. Скрытые, платные и неопубликованные записи исключаются.

Оба маршрута, `GET /api/users/search` и `GET /api/users/search/content`, принимают `limit` от 1 до 50 и непрозрачный `cursor`. По умолчанию размер страницы равен 50. Если ответ содержит `next_cursor`, передайте его в следующем запросе с тем же `q`. Курсор привязан к аккаунту, тексту запроса и разделу поиска. После проверки прав страница может быть пустой при наличии `next_cursor`. Пользователь может начать поиск заново, чтобы увидеть результаты, обновлённые после первой страницы.

Для подсказок добавьте `suggest=1`, например `GET /api/users/search/content?q=синий+кор&suggest=1`. Первые слова должны совпасть полностью, последнее сопоставляется по префиксу длиной от двух букв или цифр. Подсказки используют обычные поля `posts` или `users` и возвращают до 10 результатов после повторной проверки прав. Курсоры в режиме подсказок недоступны.

Для этого пути задайте в `[services.user.content]` числовой loopback `url` и `search_secret`, совпадающий с внутренним секретом content. Этот ключ отличается от секретов auth/search и отдельного `purge_secret`. В `services.user.search` настройте подключение к search. Межсерверный mTLS для content и search ещё не поддерживается.

Для регистрации приватного владения загрузкой media-processing использует `PUT /internal/media/{id}/reservation`, отдельный `X-Media-Service-Secret`, обязательный `X-Media-Owner` и cookie текущей сессии. User проверяет сессию через auth и совпадение владельца, создаёт приватную неготовую запись и сериализует её с жизненным циклом аккаунта. Повтор с тем же владельцем идемпотентен; чужая запись или архивированный профиль дают 409. Сам запрос не делает файл готовым и не предоставляет доступ.

В защищённом конфиге user `[services.user.media]` задаются `secret`, необязательный `previous_secret` и `client_uri`. Секреты независимы от auth, search и content. Когда для внутренних вызовов user включён mTLS, `client_uri` обязателен, отличается от auth SPIFFE URI и проверяется по цепочке сертификата. Без внутреннего mTLS запросы этого endpoint принимаются только напрямую с loopback, без доверия к заголовкам адреса. Секрет и cookie не попадать в логи. Маршрут выключен без настройки.


Обработчик фото сообщает о готовности через `PUT /internal/media/{id}/ready` с `X-Media-Service-Secret`, `X-Media-Owner` и `X-Media-Kind: photo`. User требует существующую политику с тем же владельцем, сохраняет видимость и запрещает изменение записанного типа. Старые обработчики фото без заголовка временно поддерживаются. Для существующих записей без типа срабатывает повторная доставка миграции media-processing `008`. Примените миграцию user `010` и разрешите роли user изменение колонок `media_permissions.ready` и `media_permissions.media_kind` до обновления media-processing. При запросе файла продолжают действовать проверки сессии и профилей.

Миграция `009` добавляет необратимый отзыв доступа по ID файла. После `PUT /internal/media/{id}/revoke` с учётными данными media и владельцем user закрывает выдачу и отклоняет новые запросы готовности или резервирования с тем же ID. Роль user должна иметь право вставлять `revoked_at` и обновлять `revoked_at`, `ready`, `visibility`. Очистка записей отзыва при окончательном удалении аккаунта требует согласования с очисткой публикаций.

`GET /api/users/media/{id}/ownership` подтверждает принадлежность готового файла текущей сессии. Право просмотра другого владельца само по себе эту проверку не проходит. Content использует маршрут при изменении вложений черновика.

### Качество просмотра

После миграции 012 авторизованный пользователь может получить настройки через `GET /api/users/me/playback` и заменить их через `PUT /api/users/me/playback` с настроенным Origin и JSON, например `{"photo":"auto","video":"original"}`. Оба поля обязательны при сохранении. Допустимы `auto`, `original` и `reduced`. По умолчанию оба значения равны `auto`. Для роли user предоставьте права на чтение и обновление новых колонок users и их перенос в deleted_users при архивировании и восстановлении. При проверке вложения user передаёт выбранное для его типа качество в media.

### Аватар и баннер

Примените миграцию 013. Роли user нужны чтение, вставка, обновление и удаление для user_profile_images, а также чтение, вставка и удаление для user_profile_image_history. Загрузите фото через API media-processing и дождитесь готовности. Затем авторизованный владелец может выполнить PUT /api/users/me/profile-images/avatar или PUT /api/users/me/profile-images/banner с JSON `{"media_id":"…" }`. Маршрут принимает только готовое фото этого владельца. DELETE на том же адресе убирает фото из профиля. Повтор уже применённого изменения возвращает 204 без новой записи в истории.

Поля avatar_media_id и banner_media_id доступны в GET /api/users/me и GET /api/users/{id}/profile. Для выдачи предпросмотра используется `/internal/profiles/{id}/files/{media}/preview` в media. Этот путь требует внутренний секрет и действующую сессию. Media проверяет через user, что оба аккаунта доступны и фото сейчас используется в профиле.

GET /api/users/me/profile-images/history возвращает до 20 событий владельца и необязательный курсор next для следующего запроса с параметром before. Поле available показывает, пригодно ли фото для повторной установки через PUT. Снятие фото с профиля сохраняет загрузку для повторного использования. Для физического удаления владелец использует DELETE /api/media/uploads/{id}, после которого фото перестаёт выдаваться. История и настройки сохраняются при архивировании аккаунта и удаляются при окончательной очистке.

Поиск публикаций через `GET /api/users/search/content?q=…` возвращает необязательное поле `cover_media_id`. Content берёт его из выбранной обложки или первого текущего вложения при повторной проверке публикации. Клиент запрашивает его через маршрут обложки media с ID публикации и обложки. Перед выдачей media вновь проверяет право доступа.

После проверки сессии через auth участие в публичных функциях проверяется по текущему бану аккаунта в content. `GET /api/users/me/participation` доступен служебным клиентам с cookie и возвращает ID, когда участие разрешено. В установке без content user продолжает работать автономно.

Миграция 014 сохраняет полученную от обработчика длительность видео в duration_ms. Роль user читает и обновляет эту колонку в media_permissions. Старый повтор готовности без длительности сохраняет ранее записанное значение. При несовпадении известной длительности запрос готовности возвращает конфликт.

В `GET /api/users/feed` используйте length=short или length=long для отбора по длительности. Эти фильтры выбирают только видео. Курсор одной группы не используется для другой.

`GET /api/users/feed?order=recommended` включает рекомендации. Поддерживаются kind, length, limit и cursor. Курсор привязан к зрителю, режиму и фильтрам. Без order сохраняется хронологический режим.

### Миграция жалоб на изображения профиля

Перед обновлением user примените миграцию 015 и выдайте роли обработчика жизненного цикла `EXECUTE` на `user_purge_profile_image_reports(uuid)`. Окончательная очистка удаляет жалобы на изображения удаляемого владельца. Жалобы заявителя на возраст, согласие или уже рассмотренные материалы остаются без его идентификатора.

Заявитель отправляет `PUT /api/users/me/profile-image-reports/{report}` с UUID запроса и полями `owner_id`, `slot`, `media_id`, `reason`. Первый запрос возвращает 201, точный повтор 200, конфликт 409. `GET` по тому же адресу возвращает статус только заявителю. Роли user также нужны `EXECUTE` на `user_report_profile_image(uuid,uuid,uuid,text,uuid,text)` и `user_own_profile_image_report(uuid,uuid)`. Прямой доступ к таблице жалоб запрещён проверкой запуска.

Миграция 016 добавляет очередь `GET /api/users/me/moderation/profile-image-reports` и решение `PUT /api/users/me/moderation/profile-image-reports/{case}` с `request_id` и `action` (remove или dismiss). Решение remove скрывает выбранный файл во всех слотах профиля владельца, сохраняя его замену. Выдайте роли user `EXECUTE` на `user_profile_image_blocked(uuid,uuid)`, `user_profile_image_moderation_queue(uuid)` и `user_decide_profile_image_report(uuid,uuid,uuid,text)`. Прямые права на таблицу решений не требуются.

Миграция 017 добавляет уведомления владельца `GET /api/users/me/profile-image-moderation/notices` и подачу `PUT /api/users/me/profile-image-moderation/appeals/{case}` со `statement`. Независимый модератор использует `GET /api/users/me/moderation/profile-image-appeals` и `PUT /api/users/me/moderation/profile-image-appeals/{case}` с `outcome` (upheld или reversed). Отмена снимает блокировку этого дела, сохраняя другие блокировки и текущий выбор владельца. Для роли user добавьте EXECUTE на `user_profile_image_notices(uuid)`, `user_submit_profile_image_appeal(uuid,uuid,text)`, `user_profile_image_appeal_queue(uuid)` и `user_review_profile_image_appeal(uuid,uuid,text)`.

Миграция 018 добавляет проверку доступа к изображению для media. Выдайте роли user EXECUTE на `user_profile_moderation_media_owner(uuid,uuid,uuid)`. Маршрут media `GET /internal/moderation/profile-images/{case}/files/{id}/preview` выдаёт уменьшенную копию целевого изображения для модератора открытой жалобы или независимого модератора открытой апелляции.

Для синхронизации рейтинга примените user 019–020 и content 049. Выдайте роли user EXECUTE на `user_claim_profile_points_event()` и `user_ack_profile_points_event(bigint,uuid)`, роли HTTP content — EXECUTE на `content_apply_profile_points(uuid,uuid,text,text)`. Для запуска доставки укажите одинаковый выделенный `profile_points_secret` в `[services.user.content]` и `[services.content]`. URL content должен указывать на локальный loopback. При недоступности получателя событие остаётся в очереди до повторной попытки.

С миграции 022 модератор может отправить `action: "hide"` для открытой жалобы на возраст или согласие. Скрытие прекращает выдачу файла в профиле, сохраняет его в очереди и не создаёт списание. При отклонении жалобы временное ограничение снимается. Модератор, применивший скрытие, исключён из просмотра материала и решения при последующей апелляции.

Для доставки отзывов медиа примените user 023–024 и content 052. Выдайте роли user EXECUTE на `user_claim_media_revocation()` и `user_ack_media_revocation(uuid,uuid)`, роли HTTP content — EXECUTE на `content_revoke_media_attachment(uuid,uuid)`. Настройте отдельный общий ключ `media_revocation_secret` в `[services.user.content]` и `[services.content]`. Content снимает публикации с отозванным вложением и очищает отдельные ссылки на отозванную обложку. Подтверждённое событие хранится до окончательного удаления политики файла.
