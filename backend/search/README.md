# Search: внутренний индекс кандидатов

Начальная реализация отдельного сервиса поиска на Rust и PostgreSQL. Он хранит производный индекс для `user` и `content`, а не оригинальные данные и права. Сейчас это **внутренний прототип, не готовый к публичному запуску**: индексация профилей и пользовательский API подключены; публичные кандидаты публикаций дополнительно перепроверяются content и user/auth. Пагинация, платные права и восстановление индекса ещё не реализованы. Content доставляет события отдельным издателем.

Поиск возвращает доверенному вызывающему компоненту только идентификаторы кандидатов. User проверяет сессию через auth, сверяет кандидатов с текущим ником и активным профилем и дополнительно проверяет активность аккаунта через auth. Если источник недоступен, закрытые данные не выдаются. Нельзя отдавать клиенту результаты этого API, количество, подсказки или факты совпадения до такой проверки: даже наличие совпадения может раскрыть данные. Не добавляйте в индекс закрытые тексты или персональные данные без отдельно спроектированных правил. Приватное событие должно удалять прежний доступный текст из индекса новой версией.

## Индекс и ограничения

Сейчас используется PostgreSQL full-text search с конфигурацией `simple` и индексом GIN. Он ищет слова без привязки к конкретному языку, в том числе кириллицу, но не решает автоматически морфологию, опечатки, частичные совпадения, транслитерацию и смешанную раскладку. Ранжирование и движок нужно проверить на реальных запросах; [PostgreSQL описывает полнотекстовые индексы](https://www.postgresql.org/docs/current/textsearch-indexes.html). Пагинации и общего счётчика пока нет. Результаты ограничены 50 кандидатами, и после проверки прав итоговая страница может оказаться неполной.

При офлайн-перестроении задаётся нижняя граница версий для источника: запоздавшие события с версией не выше неё подтверждаются без записи. Автоматического обнаружения отката source-БД пока нет; после отката обязательна процедура восстановления. Для каждого `(kind, id)` источник обязан выдавать монотонно растущую положительную версию состояния. Удаление сохраняет tombstone с версией и пустым текстом: более старое событие не сможет воскресить запись. Повтор той же версии с теми же данными допускается; более старая версия подтверждается без изменения индекса, а другие данные с той же версией возвращают 409. Более новая версия может восстановить запись, поэтому её право на восстановление определяет источник. Не удалять tombstones до доказанного истечения возможности доставки старых событий; политика хранения и переиндексации ещё не реализована.

Все обращения по TCP ограничены loopback. Нельзя открывать текущий HTTP или PostgreSQL без TLS в сеть: взаимный TLS, проверка конкретного вызывающего сервиса и отдельные роли источников пока не реализованы. Ключ `writer_secret` позволяет индексировать только пользователей, а отдельный `content_writer_secret` — только публикации. Если ключ контента не задан, запись публикаций закрыта. Отдельный секрет позволяет читать кандидатов. Используется одно соединение с PostgreSQL: при потере соединения процесс завершится и должен быть перезапущен средствами ОС. Автоматического восстановления и отказоустойчивости нет.

## Настройка

Сервис читает только свои поля общего `config.toml`. Пример для локального изолированного экземпляра:

```toml
[database]
driver = "postgres"
port = 5432
user = "search_app"
password = "ЗАМЕНИТЬ"
sslmode = "verify-full"

[services.search]
host = "127.0.0.1"
port = 8085
reader_secret = "ЗАМЕНИТЬ_ОТДЕЛЬНЫМ_СЛУЧАЙНЫМ_КЛЮЧОМ"
reader_secret_previous = ""
writer_secret = "ЗАМЕНИТЬ_ДРУГИМ_СЛУЧАЙНЫМ_КЛЮЧОМ"
writer_secret_previous = ""
content_writer_secret = "" # включить отдельным ключом при подключении content
content_writer_secret_previous = ""
max_connections = 128
max_db_requests = 8
header_timeout_seconds = 5
request_timeout_seconds = 10

[services.search.database]
host = "127.0.0.1"
name = "mtls_search"
sslmode = "disable"

[resources]
max_procs = 0
memory_limit_bytes = 0
```

Создайте собственную БД и отдельные роли приложения и мигратора. Примените `migrations/001_search.sql` и затем `002_version_floors.sql` от роли мигратора; роль приложения должна иметь `SELECT`, `INSERT`, `UPDATE` на `search_documents` и только `SELECT` на `search_version_floors`, без прав DDL. Обновлённый сервис не запустится без обеих записей границы версий. До миграции и восстановления остановите все старые экземпляры search: старый код не соблюдает ограничение. Миграция первоначальная, автоматического инструмента версионирования для этого сервиса пока нет. Все непустые секреты должны быть разными, 32–128 печатных ASCII-символов каждый. `content_writer_secret_previous` допустим только вместе с текущим ключом контента. Их можно сгенерировать двумя вызовами `openssl rand -hex 32`; хранить конфиг с доступом только для владельца. Для поэтапной ротации укажите новый ключ и прежний в соответствующем поле `*_secret_previous` на всех экземплярах search, перезапустите их, переведите вызывающие службы на новый ключ, а затем удалите старый ключ и повторно перезапустите search. Все непустые действующие и прежние ключи должны различаться.

`services.search.database.sslmode = "disable"` — явное исключение для PostgreSQL на loopback; текущая реализация других режимов не поддерживает и отказывается запускаться с ними. Этот параметр не меняет TLS-настройки других сервисов. Для нескольких серверов сначала необходимо реализовать PostgreSQL TLS с проверкой CA и имени сервера и межсервисный mTLS; понижать общую настройку TLS проекта нельзя.

`max_connections` — 1–4096, `max_db_requests` — 1–64, `header_timeout_seconds` — 1–60, `request_timeout_seconds` — не меньше времени заголовков и не больше 120. При исчерпании лимита БД запрос получает 503. Ограничение запросов остаётся занятым до завершения операции БД даже после отключения клиента; тайм-аут HTTP не гарантирует откат уже начавшейся записи, поэтому повторяйте её с теми же данными и версией. PostgreSQL также ограничивает время запроса тремя секундами и ожидание блокировки одной секундой. HTTP keep-alive отключён. `resources.max_procs = 0` выбирает количество потоков автоматически; заданное значение ограничено 1024. Ненулевой `memory_limit_bytes` пока только вызывает предупреждение — память ограничивается через cgroup.

Запуск из `backend/search`:

```text
cargo run -- -config ../../config.toml
```

## Внутренний API

- `PUT /internal/documents/{user|content}/{uuid}` с соответствующим типу `X-Internal-Secret` записи и JSON `{"version": 1, "text": "проверенный текст", "deleted": false}`. Для удаления: новая версия, `deleted: true` и пустой `text`. Ограничение текста — 4096 байт. Успех 204, конфликт версии 409, перегрузка или ошибка БД 503.
- `GET /internal/search?kind=user&q=слова&limit=20` с секретом чтения. Ответ — массив объектов с `id`, только кандидаты; максимум 50. Поисковый текст не должен попадать в обычные access-логи.
- `GET /health` возвращает 204, но не является проверкой актуальности индекса.

Все ответы запрещают кэширование. При завершении сервис прекращает принимать запросы и ждёт оставшиеся до 15 секунд. Изменения профилей поступают из транзакционной очереди user. После восстановления старого бэкапа требуется офлайн-переиндексация по `backend/OPERATIONS.md`; автоматическое обнаружение отката и проверка изоляции пока не реализованы, см. `BUGS.md`. Для публикаций доступен отдельный издатель content; перед публичной выдачей необходима проверка актуальных прав и восстановление индекса.

При старте search удерживает PostgreSQL advisory-блокировку на всём сроке подключения: это запрещает запустить обновлённый search во время `search-rebuild` и наоборот. Нужна прямая стабильная сессия PostgreSQL; transaction-pooling посредник использовать нельзя. Старые версии search и прямые SQL-писатели этой блокировке не следуют и должны быть остановлены и изолированы.
