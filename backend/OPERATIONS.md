# Эксплуатация auth и user

Это инструкция для будущего развёртывания. Базы, резервные копии, SMTP, сертификаты и Redis не создаются автоматически.

## Конфигурация и миграции

- Размещай отдельный `config.toml` на каждом сервере с нужными разделами; храни его и приватные ключи с ограниченными правами и вне Git. Для удалённых сервисов нужны отдельные секреты, mTLS и сертификаты с настроенными SPIFFE URI. Для удалённой БД требуется `sslmode=verify-full` и доверенный CA.
- Общие `[database].user` и `password` остаются настройкой по умолчанию. Для разных ролей можно задать пару `user` и `password` внутри `[services.auth.database]` и отдельно внутри `[services.user.database]`. Если указан только один из параметров, запуск отклоняется; пустой пароль можно задать явно для локальной БД с trust. Фактические пароли не помещай в Git.
- Для реальной изоляции у каждого сервиса должен быть **отдельный файл конфигурации** с правами, запрещающими другому сервису его чтение. Две пары паролей в одном файле изолируют роли PostgreSQL, но не скрывают пароль auth от процесса user, который может прочитать этот файл. Запускай сервисы от разных системных пользователей и не размещай учётные данные мигратора в доступных им файлах.
- Одних разных имён в конфиге недостаточно: создай отдельные роли и БД, запрети общий `CONNECT` через роль `PUBLIC`, выдай каждой роли доступ только к своей БД и проверь, что роли не являются суперпользователями и не наследуют чужие права. Для миграций можно указать `migration_user` и `migration_password` в соответствующем разделе БД; если их нет, используется пара сервиса или общая пара. Храни пару мигратора в отдельном конфиге, доступном только процессу развёртывания: этот конфиг может содержать только настройки, нужные мигратору. Роли сервиса нужны необходимые DML-права на его рабочие таблицы, но не право менять схему или историю миграций. При добавлении миграций проверяй и обновляй гранты.
- Для новой БД запускай миграции отдельно из каталогов `backend/auth` и `backend/user`: `go run ./cmd/migrate -config ../../config.toml`. Команда хранит историю и контрольные суммы, последовательно применяет изменения в транзакциях и блокирует параллельные запуски. Сервисы сами миграции не запускают.
- Независимый журнал событий auth требует собственной БД, миграции `cmd/journal-migrate`, отдельного процесса `cmd/security-journal` и наблюдения за ним. Настройка, ограничения восстановления и необходимые права описаны в `backend/auth/SECURITY_EVENTS.md`.
- Если схема уже создавалась вручную, команда откажется её изменять: сначала нужно отдельно сверить состояние БД и подготовить проверенный способ переноса истории миграций. Не заполняй таблицу истории наугад. Изменять уже применённые SQL-файлы нельзя — создавай следующую миграцию.
- До изменения схемы делай проверенную резервную копию и репетируй миграции на отдельной БД. Миграции начальной схемы рассчитаны на новую БД и не преобразуют старые таблицы с `firstname`/`lastname`.
- Синхронизируй часы серверов PostgreSQL auth и user: внутренние запросы подготовки профиля действуют только до окончания двухминутной аренды и отклоняются, если срок истёк или находится более чем на пять минут впереди часов БД user. При обновлении одновременно согласуй версии auth и user: новая версия user требует поле `valid_until` во внутреннем запросе регистрации, поэтому старый auth не сможет создавать профили до обновления. Регистрация повторится после обновления; другие API это поле не используют.
- Оба сервиса при старте проверяют основные таблицы и поля, auth также проверяет индекс очистки. Это не полная проверка всех ограничений, привилегий и содержимого БД.
- Настрой SMTP и отдельный ключ очереди по `auth/README.md`. Для замены ключа поэтапно настрой текущий и предыдущий ключи на всех экземплярах и дождись обработки старых сообщений; преждевременное удаление ключа сделает их нечитаемыми. Сертификаты и ключи mTLS сейчас перечитываются при перезапуске; используй перекрытие доверенных CA и поэтапный перезапуск.
- Перед запуском этой версии auth примени все миграции до `018` включительно. Миграция `015` отзывает сессии и повышает версию учётных данных при назначении, снятии, переносе или очистке ролей. Изменение роли требует повторного входа всех затронутых пользователей. Runtime-роли auth нужны SELECT и DELETE для `account_roles`, но не выдавай ей INSERT, UPDATE или TRUNCATE: назначением ролей управляет отдельный администратор. На временной БД проверены запрет выдачи роли runtime-пользователем и удаление модератора с ограниченными правами. Auth откажется запускаться, если обязательные триггеры отсутствуют или отключены.
- Миграция `016` добавляет транзакционный outbox событий безопасности; auth проверяет триггеры и права при старте. Для настройки Kafka, отдельных прав и метрик см. `auth/SECURITY_EVENTS.md`. При отключённой или недоступной Kafka очередь остаётся в PostgreSQL и растёт. Kafka пока не заменяет независимый журнал и сверку восстановленных данных.
- Для перехода паролей на NFC сначала обнови все экземпляры auth с `normalize_unicode = false`, затем включи настройку. Старые хеши обновляются при успешном входе; после появления версии 2 откат на старый исполняемый файл небезопасен. Подробности — `auth/passwords/README.md`.
- Redis настраивается в корневом `[redis]`: `address` в формате `host:port`, `username`, `password`, `tls`, необязательный `ca_file` и `session_cache`. Пустой `address` и остальные пустые настройки подключения отключают Redis. При `session_cache = true` используется пяти­минутный кэш идентификаторов сессий; права доступа всегда проверяются PostgreSQL. Уже существующие сессии кэшируются при следующем успешном обращении. Для удалённого Redis обязательны TLS и отдельная пара ACL; для loopback допустима локальная разработка без них. При указанном `ca_file` доверяются сертификаты этого файла. Поддерживаются прямое подключение и Sentinel; Redis Cluster и клиентские сертификаты Redis не поддерживаются.
- Для Sentinel оставь `address` пустым и задай `sentinel_master`, `sentinel_addrs` (список `host:port`), `sentinel_username` и `sentinel_password`. `username/password` используются отдельно для Redis. Удалённые Sentinel и обнаруженные ими удалённые Redis требуют TLS и обе пары ACL-учётных данных. `ca_file` используется для обоих типов соединений; сертификат каждого обнаруженного адреса должен подтверждать его имя или IP. Укажи несколько независимых Sentinel и проверь фактический failover в своей сети. Во время отказа auth использует PostgreSQL; включение Sentinel не делает Redis источником прав.
- Для ACL клиента Sentinel на проверенной версии Redis достаточно `+hello +ping +sentinel|get-master-addr-by-name +sentinel|sentinels +subscribe` и доступа к каналу `&+switch-master`. Sentinel нужны отдельные права для управления Redis и общения между Sentinel; их настраивают отдельно от приложения по [документации Redis](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/). Не разрешай приложению публиковать в `__sentinel__:hello`; ограничивай доступ к Sentinel и используй доверенные сертификаты.
- Ограничь Redis ACL ключами `~mtls:auth:ip-guard:v1:*`, а при кэше сессий также `~mtls:auth:session-cache:v1:*`, и командами `+hello +ping +eval +evalsha +get +getrange +incr +pttl +pexpire +set`; конфигурацию ACL и TLS проверяй на своей версии Redis. Ограничитель сохраняет только HMAC IP и счётчик на 60 секунд; кэш — HMAC от хеша токена и UUID сессии на пять минут. Сырого токена и ID пользователя Redis не получает. При сбое или неверной записи Redis auth использует PostgreSQL, при сбое PostgreSQL доступ по кэшу не предоставляется. Redis следует сетево изолировать и ограничить по памяти; `/health` и `/ready` его не проверяют.
- Redis здесь хранит только временные подсказки и ограничители, а не источник прав. Продумай сохранение и удаление его снимков, журналов и реплик: TTL ключей сам по себе не удаляет старые резервные копии. Для кэша сессий не включай долговременное сохранение без отдельной политики удаления данных. Результаты локального сравнения и ограничения скорости — в `REDIS_PLAN.md`.

## Резервные копии

Для изолированной проверки восстановленной копии останови все экземпляры auth и user и закрой внешний доступ к восстановленным БД. В отдельных конфигурациях каждого экземпляра включи `[services.auth].recovery_mode = true` и `[services.user].recovery_mode = true`, затем запусти оба сервиса в изолированной сети. В этом режиме доступен только `GET /health`; `/ready`, публичные и внутренние API отвечают `503`, а фоновые обработчики и очистка не запускают работу. Проверено на работающих сервисах с незавершённой задачей удаления и на восстановленных копиях обеих БД: старые сессии и уже удалённый аккаунт присутствовали в копии, но через API в режиме изоляции не открывались. Конфигурация не хранится в БД: режим **не включается автоматически** при восстановлении, и старые экземпляры кода его не поддерживают. Прямой доступ к БД режим тоже не блокирует.

Проверяй и сверяй восстановление с независимыми записями об удалениях, сменах паролей и отзывах, созданными после момента копии. Без надёжного независимого источника этих изменений нельзя определить, какие данные и доступы устарели; не выключай режим и не открывай восстановленные данные пользователям. Перед выводом из режима восстанови согласованное состояние auth и user, проверь сроки удаления и отзови восстановленные сессии; переключай все экземпляры согласованно. Обычный бэкап и этот режим не заменяют журнал последних изменений и не решают удаление данных из резервных копий.

- Снимай отдельные согласованные копии БД auth и user; не считай, что два независимых `pg_dump` дают единый моментальный снимок между сервисами. Перед восстановлением согласуй отключённые аккаунты и незавершённые операции, затем проверь и при необходимости отзови сессии.
- Для логической копии PostgreSQL можно использовать `pg_dump --format=custom --file=<путь_к_копии> --dbname=<имя_базы>`, задавая адрес, пользователя, `PGSSLMODE=verify-full` и `PGPASSFILE` через защищённую среду. Файл паролей должен иметь права `0600`; не добавляй пароль в командную строку. Копии должны быть зашифрованы, ограничены по доступу и проверены восстановлением в изолированной БД через `pg_restore`.
- На временных отдельных БД проверено создание и восстановление копий обеих схем через `pg_dump -Fc` и `pg_restore --single-transaction`, когда записи остановлены: восстановились связанные учётная запись и профиль, а также история миграций. Это проверка базового сценария, а не подтверждение согласованного восстановления при работающих сервисах или после любых сбоев.
- После восстановления старой копии позднейшие смены пароля, отзывы сессий и удаления могут отсутствовать. До открытия доступа обязательно отзови восстановленные сессии; сами по себе старые копии не позволяют определить все последующие изменения. Без надёжного отдельного журнала удалений и проверенной процедуры сверки нельзя безопасно возвращать восстановленные аккаунты в публичную эксплуатацию. Журнал и процедура пока не реализованы.
- **Срок удаления и копии:** обычный срок хранения резервной копии сам по себе не гарантирует удаление пользовательских данных ровно через два месяца после удаления аккаунта. До публичного запуска необходимо выбрать и проверить механизм удаления данных из копий или криптографического уничтожения ключей, включая старые копии и реплики. Не обещать окончательное удаление из всех копий, пока это не реализовано.
- Не сохраняй реальные дампы, сертификаты с приватными ключами и секреты в Git. Временные тестовые БД, сокеты, логи и результаты проверок агентов находятся только в `tmp/` и удаляются после работы.

## Мониторинг и отказы

`/health` проверяет подключение сервиса к своей БД; `/ready` дополнительно проверяет авторизованное внутреннее соединение с зависимым сервисом. Эти endpoints не проверяют SMTP, настройки бэкапов или накопленные задания. Следи за доступностью БД и сервисов, возрастом незавершённых регистраций, ошибками SMTP, повторными операциями жизненного цикла и накоплением удалённых аккаунтов. При отказе user аккаунты с незавершённым удалением и восстановлением остаются отключёнными, а задания повторяются после восстановления связи. Полная система мониторинга и алертов, безопасное восстановление после потери позднейших изменений и промышленное развёртывание Redis ещё не реализованы; см. `TASKS.md`.

Auth предоставляет агрегированные показатели очередей в формате Prometheus через `GET /internal/metrics`. Доступ защищён теми же секретом и, при включённом mTLS, идентичностью сертификата, что и прочие внутренние вызовы user → auth. Показатели не содержат идентификаторов, почты или токенов; они включают ожидающую и приостановленную подготовку профиля, письма и операции жизненного цикла. Значение приостановленных регистраций больше нуля требует разбора; длительно растущие очереди также требуют оповещения. Инструмент мониторинга и правила оповещений ещё нужно настроить для конкретного развёртывания. При нескольких экземплярах auth эти показатели отражают общую БД, поэтому их не следует суммировать между экземплярами.

Для межсервисных запросов auth и user предоставляют защищённый `GET /internal/metrics`: `mtls_auth_peer_requests_total` / `mtls_auth_peer_failures_total` и `mtls_user_peer_requests_total` / `mtls_user_peer_failures_total`. Ошибками считаются сбой транспорта и HTTP 5xx; другие ответы и проверка `/ready` в эти показатели не входят. Счётчики относятся к процессу и сбрасываются при перезапуске. Настрой частоту сбора и оповещения в своей системе мониторинга; секрет и, при mTLS, сертификат мониторинга должны удовлетворять требованиям внутреннего peer.

При включённом Redis дополнительно доступны счётчики `mtls_auth_redis_guard_blocked_total` и `mtls_auth_redis_guard_fallback_total` для каждого процесса auth. Рост fallback означает ошибку Redis или временный отказ от обращения к нему после ошибки; следует настроить оповещение и проверить соединение, ACL и TLS. Эти счётчики процессов допустимо суммировать.

При включённом кэше сессий доступны счётчики `mtls_auth_session_cache_hits_total`, `mtls_auth_session_cache_misses_total` и `mtls_auth_session_cache_failures_total`. Они относятся к отдельному процессу; попадание в кэш не означает успешной аутентификации без PostgreSQL.

Подготовка профиля при регистрации приостанавливается после 100 попыток: учётная запись остаётся отключённой, данные не удаляются, в журнале появляется сообщение `registration provision paused` либо `registration activation paused`. Число ожидающих ручного разбора записей можно проверить в базе auth:

```sql
SELECT count(*) FROM registrations r
JOIN credentials c ON c.user_id = r.user_id
WHERE r.confirmed_at IS NOT NULL AND NOT c.enabled AND r.provision_attempts >= 100
    AND (r.provision_lease_until IS NULL OR r.provision_lease_until <= clock_timestamp());
```

После устранения причины и проверки конкретной регистрации оператор может возобновить её, сбросив счётчик только для её `user_id` и только после окончания аренды обработчика. Не удаляй регистрацию и не включай учётную запись вручную: профиль может уже быть создан после потерянного ответа.

```sql
UPDATE registrations r SET provision_attempts = 0, provision_after = CURRENT_TIMESTAMP,
    provision_lease_id = NULL, provision_lease_until = NULL
WHERE r.user_id = :'user_id' AND r.confirmed_at IS NOT NULL AND r.provision_attempts >= 100
    AND (r.provision_lease_until IS NULL OR r.provision_lease_until <= clock_timestamp())
    AND EXISTS (SELECT 1 FROM credentials c WHERE c.user_id = r.user_id AND NOT c.enabled);
```

## Отзыв сессий восстановленной копии

После восстановления и применения auth-миграции `018` останови **все** экземпляры auth и user, заблокируй другие записи в auth-БД и включи `recovery_mode = true` для обоих сервисов в отдельном конфиге команды. Выполни из `backend/auth` `go run ./cmd/recovery-check -config ../../config.toml -invalidate-sessions`. Операция в одной транзакции блокирует записи в таблицу сессий и устанавливает поколение строго больше всех имеющихся, в том числе при несовпадении отдельных частей копии. Старые токены перестают проходить проверку; новое поколение не зависит от часов и не создаёт события на каждую сессию, поэтому не пересекается с версиями независимого журнала.

Для команды используй отдельную привилегированную роль: SELECT на `session_epoch.id`, `session_epoch.generation`, `sessions.recovery_generation`, UPDATE на `session_epoch.generation` и UPDATE на таблицу `sessions` для блокировки. Табличное UPDATE на `sessions` является сильным правом; не выдавай эти дополнительные права роли, предназначенной только для сверки. Обычному auth нужен SELECT на `session_epoch`; право менять поколение ему не требуется. Команда проверяет флаги конфига, но они **не останавливают** работающие процессы и прямые записи. Запуск при работающих сервисах может разорвать активные запросы; повторный запуск отзовёт также сессии, созданные после предыдущего запуска.

Поколение хранится в auth-БД и может откатиться вместе с новой старой копией. Поэтому операцию необходимо выполнять после **каждого** восстановления, до открытия API. Ни один старый бинарник auth, который не проверяет поколение, после операции запускать нельзя: он может снова принять старый токен. Это не восстанавливает потерянные изменения паролей или удалений и само по себе не разрешает снимать изоляцию.

## Непрерывное восстановление PostgreSQL

Проверка на временном PostgreSQL: после создания базы auth и user сделана физическая копия; затем изменён пароль, отозвана сессия и профиль перенесён в архив. Восстановление копии с непрерывным архивом WAL вернуло изменённый пароль, отозванную сессию и архивный профиль. Отдельно проверены два независимых экземпляра PostgreSQL: воспроизведение их WAL, изоляция, отзыв старых сессий и восстановление аккаунта. При намеренно неполном архиве были получены взаимно совпадающие, но устаревшие копии; локальная сверка не может доказать, что более поздние изменения не потеряны. Проверки не подтверждают готовность фактической инфраструктуры.

Для продакшена нужны регулярные проверенные физические резервные копии и непрерывный защищённый архив WAL вне отказового домена основного сервера. При раздельных PostgreSQL у auth и user каждый экземпляр требует собственного непрерывного архива, а после восстановления необходимо отдельно сверить состояние межсервисных операций. Если необходимо не терять подтверждённые транзакции при потере сервера, требуется подходящая синхронная репликация и проверка её настроек и фактических отказов; один асинхронный архив может отставать. Подробности и требования непрерывной цепочки — [документация PostgreSQL](https://www.postgresql.org/docs/current/continuous-archiving.html).

Для проверки соответствия профилей после восстановления останови все записи в обе базы и запусти из `backend/auth` команду `go run ./cmd/recovery-check -config ../../config.toml` с `recovery_mode = true` для обоих сервисов. Для неё необходимы SELECT на auth `credentials`, `registrations`, `account_deletions`, `account_roles` и user `users`, `deleted_users`, `registration_provisions`, `account_lifecycle_operations`. Команда проверяет существование и состояние профиля, отсутствие ролей у удалённых аккаунтов, время удаления, незавершённые операции и регистрацию, а также записи user для безопасного повтора операции. При расхождении или незавершённых операциях она возвращает код 1; даже если проверенные состояния совпадают, она возвращает код 2: полнота источников не доказана и открывать сервисы нельзя. Код 0 используется для успешной отдельной команды `-invalidate-sessions` и не является подтверждением полноты восстановления. Сообщения не содержат ID пользователей. При необходимости можно добавить `-issue-file /защищённый/путь/issue.json`: команда создаст новый файл с правами не шире `0600` и запишет ID и вид первого расхождения; существующий файл она не перезапишет. Это персональные данные: ограничь доступ, после использования удали файл и при следующих проверках указывай новый путь. Для незавершённых операций без расхождения файл не создаётся. Сервисы и БД могут располагаться на разных узлах; конфиг команды должен содержать адреса и отдельные доступные ей пары учётных данных. Остановка записей обязательна: read-only снимки двух БД не атомарны между серверами, а флаги конфига сами по себе не останавливают другие экземпляры. Проверка не сравнивает содержимое профилей, не восстанавливает изменения и не доказывает полноту копий.

Восстанавливай обе базы в изолированной сети и включай режим восстановления у всех экземпляров auth/user; не открывай сервисы по одному только факту успешного запуска PostgreSQL. Отдельная сверка `security-journal -compare-source` обнаруживает часть потерянных и конфликтующих событий, но не доказывает полноту WAL, журнала или межсервисной истории. При пропуске WAL, отсутствии доказанной точки восстановления либо несогласованных состояниях копии остаются изолированными. Полная автоматическая сверка auth/user и проверенная политика удаления пользовательских данных из архивов пока не реализованы.

## Media и поиск профилей

Перед обновлённым user примените миграции до `008`, для content — до `004` и выдайте runtime-роли DML на `media_permissions`, `media_permission_grants`, `user_search_events`, `content_purge_events` и USAGE на `user_search_events_version_seq`; схему меняет отдельная роль мигратора. По умолчанию политики новых медиа закрыты, а доверенная регистрация файлов и управление правами ещё не подключены. При удалении автора сведения о принадлежащих файлах и задача очистки сохраняются до физического удаления медиа, которое ещё не реализовано.

Для индексации профилей настройте одинаковые ключи чтения и записи в `[services.search]` и `services.user.search.url` на локальный search. User проверяет кандидатов по собственной БД и auth и отправляет изменения из транзакционной очереди с повтором. Не удаляйте необработанные события вручную. Для восстановления старого бэкапа есть офлайн-процедура ниже; автоматическая проверка изоляции и обнаружение отката ещё не реализованы: см. `BUGS.md`. Content требует отдельные ограниченные роли БД для черновиков и очистки; права и проверки описаны в `backend/content/README.md`. Media проверяет каждое новое обращение к файлу через user и auth, но передача между этими сервисами пока рассчитана только на loopback; конфигурация сертификатов auth/user сама по себе не добавляет mTLS в media/search.

### Офлайн-перестроение индекса пользователей

После отката user-БД нельзя просто продолжать отправку старых версий в существующий search: они будут считаться устаревшими. Остановите **все** экземпляры user, search и любые другие процессы, способные записывать пользовательский индекс, завершите уже начатые запросы и изолируйте их от обеих БД. Проверьте, что известны адреса и имена именно нужных user и search БД. Команда проверяет отсутствие других сессий в обеих БД и откажет при обнаружении хотя бы одной, в том числе административной. Обновлённые экземпляры search дополнительно удерживают общую advisory-блокировку: команда не запустится, пока search работает, а новый search откажется запускаться во время перестроения. Прямые SQL-писатели, старые версии search и уже отправленные внешние запросы блокировку не соблюдают.

Используя отдельные роли с необходимыми правами на чтение/блокировку и изменение таблиц индекса и очереди, запустите из `backend`:

```text
go run ./user/cmd/search-rebuild -config ../config.toml -isolated
```

Команда блокирует таблицы, повышает последовательность user выше существующих версий search, записывает нижнюю границу версий в search, заменяет очередь снимком активных профилей и очищает только `kind=user`. Обновлённый search игнорирует запоздавшие события не выше этой границы, включая события удалённых пользователей. Индекс публикаций не очищается. Базы независимы и не образуют одну распределённую транзакцию: при ошибке или прерывании между фиксациями **не запускайте сервисы**, сохраните изоляцию и повторите команду до успеха. Значение последовательности может увеличиться даже после отката. После успеха запустите search, затем user с включённым publisher, проверьте опустошение `user_search_events`, соответствие результатов актуальным профилям и продолжайте работу только после проверки. Большая база потребует времени и места; сейчас жёсткий срок операции — пять минут.

Флаг `-isolated` — явное подтверждение оператора; проверка сессий и блокировка обновлённого search не гарантируют остановку старых версий, прямых SQL-писателей или сетевых отправителей. Перед использованием обновите все экземпляры search; требуется постоянное соединение с PostgreSQL, а не transaction-pooling посредник. Автоматическое обнаружение восстановления и защита от ошибочного запуска ещё не реализованы. Не используйте процедуру, пока нельзя гарантировать отсутствие старых или повторно доставляемых событий.

### Сверка content после восстановления копии

Старая копия content может содержать записи аккаунта, окончательно удалённого после создания копии. Нельзя выводить её в сеть без сверки. Сначала восстановите и независимо проверьте актуальность и полноту auth по существующей процедуре recovery и независимым источникам. Если полноту доказать нельзя, неизвестный автор может означать потерю данных auth: удалять его контент нельзя.

Для проверки процесса в изолированной сети включите `[services.content].recovery_mode = true` на каждом экземпляре. При этом все API, кроме `GET /health`, возвращают 503. Восстановление само не включает флаг; старый код его не поддерживает, а прямые соединения с PostgreSQL он не закрывает. Перед запуском офлайн-сверки всё равно остановите процессы и остальные соединения, а после неё не отключайте режим без проверки полноты источника и удаления.

Остановите и изолируйте **все** клиенты auth и content, дождитесь завершения запросов и проверьте адреса и имена обеих БД. Команда отказывает при других подключениях, пустой таблице credentials, row-level security и наличии медиа у подлежащего очистке автора; она не предотвращает новые подключения и не доказывает полноту auth. Перед сверкой примените auth-миграцию `019`. Для отдельной роли сверки нужны `SELECT (user_id)` на `credentials` и `SELECT` на представление `content_reconciliation_authors`, без доступа к паролям и почте; также нужны права блокировки/очистки таблиц content, включая `content_author_purges`. Команда сначала получает блокировки схемы без ожидания и проверяет блокировку `credentials`, затем фиксирует снимок и проверяет RLS. Это не заменяет сетевую изоляцию и остановку писателей.

Из `backend` сначала выполните без удаления:

```text
go run ./content/cmd/reconcile-authors -config ../config.toml -isolated -verified-auth
```

После проверки результата и только при подтверждённой полноте источника повторите с `-apply`. Сверка сохраняет авторов, присутствующих в auth, включая архивные аккаунты, и транзакционно удаляет данные только тех, кого в auth нет. При ошибке или обнаруженных медиа вся транзакция откатывается; оставьте content изолированным и решите проблему с источником или удалением файлов. Флаги подтверждают действия оператора и не являются доказательством корректности копий. Автоматическое обнаружение восстановления и физическое удаление медиа ещё не реализованы.

Миграцию `backend/search/migrations/002_version_floors.sql` необходимо применить до запуска обновлённого search и `search-rebuild`. Runtime-роли search нужен SELECT на `search_version_floors`; роль офлайн-восстановления должна читать и изменять её. Остановите все старые версии search и писателей перед миграцией и перестроением: прежний код не проверяет нижнюю границу версий.


### Повторная доставка решений по изображениям профиля

Если восстановили только content, подтвердите полноту актуальной базы user и завершите основную сверку content по инструкции выше. Оставьте content в recovery mode. В этом режиме доступны health, маршрут доставки решений с отдельным `profile_points_secret` и маршрут отзыва вложений с отдельным `media_revocation_secret`. Остальные маршруты возвращают 503.

После миграции user 021 роль администратора БД может повторно поставить в очередь подтверждённые события через `UPDATE user_profile_moderation_outbox SET delivered_at=NULL WHERE delivered_at IS NOT NULL`. Дождитесь, пока `SELECT count(*) FROM user_profile_moderation_outbox WHERE delivered_at IS NULL` вернёт ноль. Затем сверьте итоговые решения и балансы до открытия API. События, присутствующие в восстановленной базе content, придут повторно без второго начисления или вычета. Пропущенные списания применяются по политике восстановленной базы. Для восстановления точных исторических балансов и предупреждений нужен полный WAL content.
