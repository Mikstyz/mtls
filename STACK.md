# Стек и практики проекта

Файл фиксирует фактически используемые технологии и отдельно отмечает запланированные решения. Детали запуска — `backend/OPERATIONS.md`, задачи — `TASKS.md`.

## Размещение

Проект использует самостоятельно разворачиваемые компоненты: на своих серверах или ПК. Базы, Redis, Kafka, журнал, хранилище медиа и будущие инфраструктурные службы должны быть доступны для собственного размещения и находиться под управлением владельца. Единственное допускаемое исключение — внешний сервис для отправки почты. Других обязательных обращений к API сторонних сервисов во время работы проекта не предусматривается. Сервисы проекта могут обращаться к собственным API друг друга, в том числе на разных серверах.

SMTP и DNS как сетевые протоколы могут взаимодействовать с почтовой инфраструктурой и DNS пользователей: это необходимо для доставки писем и не означает подключение стороннего API. Почтовый сервер может быть собственным или внешним; домен, сеть и сертификаты ещё нужно настроить.

## Технологии

- **Backend:** отдельные Go-сервисы `auth` и `user`, Go workspace и общие пакеты в `backend/shared`. Каждый сервис владеет своей БД и может работать на отдельном сервере. `content` — начальный Go-сервис каталога с приватными черновиками; публикация, права, пользовательские ленты и бизнес-логика ещё не завершены.
- **Данные:** PostgreSQL — постоянные данные, учётные записи и источник прав сессий. Redis — необязательные ограничитель потока и краткоживущие подсказки для поиска сессий; поддерживается Sentinel. Права на каждом запросе проверяет PostgreSQL.
- **События:** Apache Kafka выбрана для доставки событий между сервисами и в независимое хранилище журнала. Транзакционный outbox хранится в БД сервиса, чтобы изменение и запись события фиксировались вместе. Auth записывает события в PostgreSQL outbox и умеет отправлять их в Kafka; отдельный потребитель сохраняет события и позиции Kafka в PostgreSQL; проверка полноты источника и восстановление ещё находятся в разработке.
- **Медиа и поиск:** начат внутренний сервис выдачи файлов на Rust; отдельно начат search на Rust с производным PostgreSQL FTS-индексом; качество и выбор движка требуют проверки нагрузкой. Приём и обработка медиа относятся к отдельному контуру `backend/media-processing` на Go/Linux. В нём начаты хранение, обработка фото и расчёт размеров видео; загрузка и управление жизненным циклом ещё не подключены. Подробности — `TASKS.md` и README контура.
- **Frontend:** React 19 и Vite 6, JavaScript. Клиент пока не интегрирован с API.
- **Reverse proxy:** Rust, отдельный сервис; вне текущих работ по backend API.
- **Интерфейсы:** HTTP/JSON, PostgreSQL, SMTP с STARTTLS; для удалённого взаимодействия auth/user используются TLS/mTLS и отдельные межсервисные секреты.

## Практики

- **Структура кода:** исполняемые команды остаются в `cmd`, внутренняя логика — в тематических пакетах `internal`; пакеты выделяются по ответственности, без искусственных слоёв. Ориентиры — [организация Go-модуля](https://go.dev/doc/modules/layout), [стиль Go от Google](https://google.github.io/styleguide/go/decisions) и [Rust API Guidelines](https://rust-lang.github.io/api-guidelines/). В Rust HTTP-обработчики, доменная логика и доступ к данным разделяются там, где это упрощает код; точка запуска связывает компоненты и конфигурацию.

- **Независимость сервисов:** отдельные настройки, базы и учётные данные там, где нужна изоляция; не полагаться на общий диск или размещение на одной машине.
- **Согласованность:** транзакции внутри сервиса, идемпотентные межсервисные операции, ограниченные повторы с backoff и jitter. Для событий — outbox, повторная доставка, идемпотентные потребители и явная проверка порядка; Kafka не заменяет транзакцию PostgreSQL или резервные копии.
- **Безопасность:** параметризованные SQL-запросы, ограничение ввода и времени запросов, принцип минимальных привилегий, авторизация на сервере, Origin/CSRF для cookie, Argon2id, хранение хешей токенов, TLS/mTLS и секреты вне Git. Имена устройств и IP не доказывают подлинность устройства.
- **Сессии и приватность:** отзыв действует через PostgreSQL, онлайн определяется по активным сессиям и настройкам видимости. Логи и события не должны содержать пароли, токены и лишние персональные данные.
- **Восстановление и удаление:** пользователь восстанавливает аккаунт 14 суток, модератор — в пределах двух календарных месяцев с удаления. Восстановленную копию изолировать до сверки позднейших изменений; независимый журнал, политика удаления из бэкапов и проверка полноты доставки ещё не завершены.
- **Код и проверка:** стандартное форматирование языка, читаемые смысловые блоки, контексты и тайм-ауты, защита от инъекций и реальных атак. Значимые проверки писать от ожидаемого поведения; временные тесты и БД удалять после проверки согласно `AGENTS.md`.
- **Эксплуатация:** отдельные роли PostgreSQL, секреты и сертификаты; проверяемые миграции и восстановление, наблюдаемость без секретов. Реальные сетевые границы, выпуск сертификатов, оповещения и нагрузку нужно проверить при развёртывании.
