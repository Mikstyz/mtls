# MTLS

MTLS — самостоятельно размещаемая площадка для фото и видео. Требования, правила работы и критерии готовности API собраны в [TASKS.md](TASKS.md). Инструкции по запуску и восстановлению находятся в [backend/OPERATIONS.md](backend/OPERATIONS.md).

## Backend

- `backend/user`, `backend/auth`, `backend/content` — отдельные Go-модули для пользователей, авторизации и контента или продуктов.
- `backend/proxy` — отдельный Rust-пакет для будущего обратного прокси; в `src` подготовлены каталоги конфигурации, маршрутизации, балансировки, подключения к сервисам и middleware.
- `backend/shared` — отдельный Go-модуль для общего кода, когда он действительно понадобится. `backend/api` — место для контрактов, `backend/deployments` — для конфигурации развёртывания.
- `backend/go.work` объединяет Go-модули при локальной разработке. Имена модулей `mtls/...` пока условные: перед публикацией или самостоятельным подключением модулей их следует заменить на реальные пути репозиториев. Общий код не должен объединять бизнес-логику независимых сервисов.

## Приложения

- `frontend/src` — React: `components`, `pages`, `hooks`, `services`, `assets`, `styles`. Публичные статические ресурсы находятся в `frontend/public`.

Пустые каталоги не сохраняются в Git до появления в них файлов. Структуру можно менять по мере появления реальных требований; сами папки не обеспечивают независимость сервисов. Границы данных, контракты, развёртывание и взаимодействие сервисов предстоит определить отдельно.

## Инструменты

Для auth и user необходим Go 1.26 или новее; также понадобятся Rust с Cargo и Node.js 20.19+ или 22.12+. Во фронтенде зависимости устанавливаются командой `npm install` из каталога `frontend`. Content поддерживает черновики и поиск публичных кандидатов. За подготовку фото отвечает Go-обработчик, за выдачу и поиск — отдельные Rust-сервисы.

## Конфигурация сервисов

Корневой `config.toml` — локальный файл с настройками и секретами; он исключён из Git. Общий раздел `[database]` задаёт драйвер, порт, TLS-режим, пользователя и пароль БД; название и адрес БД остаются у каждого сервиса. Разделы `[http]` и `[resources]` также общие; адреса сервисов и адреса их межсервисных соединений настраиваются отдельно. На разные машины можно положить отдельные копии с нужными разделами.

Для удалённых auth и user настрой в `[security]` два разных секрета `auth_to_user_secret` и `user_to_auth_secret`, одинаковые в конфигурации обоих сервисов, и отдельный `rate_limit_secret` для auth. Прежний общий `internal_secret` допускается только для локальных межсервисных соединений. Секреты нельзя публиковать; удалённые межсервисные URL должны использовать HTTPS, а PostgreSQL — `sslmode = "verify-full"`. `127.0.0.1` подходит только для соединений внутри одной машины.

Собственный HTTPS и mTLS внутренних вызовов настраиваются в `[services.auth.tls]` и `[services.user.tls]`; для удалённых сервисов mTLS обязателен, локально необязателен. Для регистрации и восстановления пароля нужны SMTP и отдельный ключ очереди в `[services.auth.registration]`; параметры, ограничения mTLS и локальный список запрещённых паролей описаны в `backend/auth/README.md`. Redis можно подключить как дополнительный ограничитель потока и кэш идентификаторов сессий через `[redis]`; проверка и отзыв сессий остаются в PostgreSQL. Подробности — в `REDIS_PLAN.md`.

`[resources].max_procs` — значение GOMAXPROCS, `memory_limit_bytes` — мягкий лимит памяти Go в байтах. При 0 число процессоров выбирается с учётом квоты контейнера, а память — автоматически: 25% лимита cgroup или физической памяти при его отсутствии. Переменные среды `GOMAXPROCS` и `GOMEMLIMIT` имеют приоритет над автоматикой, но не над явно заданными значениями конфига. Лимит Go не является жёстким ограничением памяти процесса; контейнерные лимиты и потребности других процессов нужно настраивать отдельно.

В `[http]` указывается разрешённый Origin сайта и `cookie_secure`. Для HTTPS используйте `cookie_secure = true`; `false` допускается auth только для разработки на localhost. Для запуска нужны заполненные имена баз данных и общие данные подключения. Прокси пока не реализован; auth и user можно запускать отдельно после применения их миграций:

```sh
cd backend/auth
go run ./cmd/server -config ../../config.toml
```

В другом терминале из `backend/user` выполните ту же команду. Подробности API и незавершённой функциональности — в `backend/auth/README.md` и `backend/user/README.md`. Общие учётные данные БД пока подключены только в auth и user; content ещё не адаптирован к этой структуре конфигурации.

Порядок миграций, резервные копии и эксплуатационные ограничения описаны в `backend/OPERATIONS.md`.
