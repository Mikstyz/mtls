# Redis для проекта

План для платформы с пользовательскими профилями и платным контентом. Auth может использовать Redis как дополнительный ограничитель потока по IP и кэш идентификаторов активных сессий. PostgreSQL остаётся единственным источником решения о доступе, сроках и отзыве; контент в Redis пока не хранится.

## Реализованный кэш сессий

При настроенном прямом адресе Redis либо Sentinel и включённом `[redis].session_cache` auth записывает идентификатор новой сессии под HMAC-ключом, производным от хеша случайного токена. Сырого токена, его хеша и ID пользователя в Redis нет. Запись живёт не более пяти минут с создания и не продлевается чтением. Уже существующая сессия попадает в кэш при первом успешном обращении; принудительно завершать существующие устройства не нужно.

Redis возвращает только подсказку для поиска строки. PostgreSQL **на каждом запросе** повторно проверяет хеш токена, пользователя, отзыв, абсолютный срок и неактивность; Redis сам по себе не может выдать доступ. Отозванная запись может физически оставаться в Redis до TTL, но PostgreSQL её отклоняет. При ошибке, отсутствии или повреждении подсказки выполняется обычный поиск в PostgreSQL. Если PostgreSQL недоступна, кэш доступ не выдаёт. Два экземпляра должны использовать одинаковый `rate_limit_secret`: от него с отдельной криптографической меткой выводится ключ HMAC кэша.

Проверены два экземпляра, порча подсказки, недоступность Redis и PostgreSQL, истечение при ожидании блокировки, смена и сброс пароля, отзыв, удаление и восстановление аккаунта с сохранившимися старыми Redis-записями. Дополнительно на локальном стенде с primary, одной репликой и тремя Sentinel проверено автоматическое повышение реплики после остановки primary: при недоступности прежнего адреса auth использует PostgreSQL, а после ручного подключения к новой primary отозванная сессия с реплицированной подсказкой остаётся недействительной. Auth поддерживает прямой адрес либо группу Sentinel: при Sentinel клиент узнаёт новый primary и переподключается автоматически. Проверены переключение с тремя Sentinel и одной репликой, восстановление кэша, отзыв сессии со старой подсказкой, а также отдельное переключение с TLS и ограниченными ACL. При остановке двух из трёх Sentinel и primary проверены отсутствие повышения без кворума, fallback PostgreSQL и сохранение отзыва; после возобновления Sentinel восстановилось переключение и подключение кэша. При искусственной паузе Sentinel входили в TILT; с слишком коротким `down-after-milliseconds` реплика не прошла отбор, поэтому параметры отказа нужно проверять вместе. Приостановка процессов имитирует недоступность, но не покрывает произвольные сетевые разделения и промышленное HA.

Кэш не гарантирует ускорения: в локальном последовательном тесте с одной сессией PostgreSQL без кэша занимал примерно 1,16–1,19 мс на запрос, с Redis — 1,24–1,34 мс. В отдельном локальном синтетическом тесте с 20 000 дополнительных записей сессий, 100 активными сессиями и 16 параллельными клиентами PostgreSQL обеспечил 5 118–5 318 проверок/с (p95 5,9–6,1 мс), с Redis — 3 202–3 249 проверок/с (p95 8,6–8,8 мс). Тест не моделирует удалённые серверы, реальное распределение запросов или большие нагрузки и не позволяет делать общий прогноз. Измеряй свою нагрузку; если кэш не полезен, отключи его через `session_cache = false`.

## Реализованная защита потока

При настроенном прямом адресе Redis либо Sentinel auth использует Redis перед основным ограничителем. Redis атомарно хранит счётчик на минуту под HMAC-хешем IP и отсеивает поток после 200 запросов; PostgreSQL остаётся обязательным и применяет основной лимит 100 запросов по IP и 10 по идентификатору. Если Redis недоступен или вернул ошибку, auth продолжает проверку через PostgreSQL; если PostgreSQL недоступна, защищённый запрос отклоняется. Счётчики Redis не содержат IP, логины, cookie или токены.

Из-за независимых окон и сбоев Redis может временно отклонить запрос раньше, чем основной лимит PostgreSQL; это дополнительное ограничение доступности, а не разрешение сверх лимита. Ограничитель использует непосредственный IP соединения и требует отдельной настройки доверенного IP после появления прокси. Разные экземпляры auth должны использовать один стабильный `rate_limit_secret`. Настройки Redis, Sentinel, ACL и метрики описаны в `backend/OPERATIONS.md`. Sentinel доверяется как источник адресов: ограничивай доступ к нему и не выдавай обычным приложениям доступ к каналу `__sentinel__:hello`, через который Sentinel обменивается топологией.

## Что рассмотреть

- **Сессии и устройства:** быстрый доступ к активным сессиям, отдельный индекс устройств пользователя, автоматическое истечение и активность. Нужно сохранить и абсолютный срок сессии, и срок бездействия, отзыв отдельной сессии и всех устройств при сбросе пароля или удалении аккаунта. Отзыв должен работать между экземплярами auth и не возвращать старые токены после сбоя.
- **Онлайн-статус:** краткоживущая активность по устройствам; пользователь онлайн, если активна хотя бы одна разрешённая сессия. Учитывать настройки приватности и немедленный отзыв.
- **Популярные пользователи и посты:** рейтинги за выбранные периоды можно считать по агрегированным событиям и хранить в sorted sets. Окончательную формулу популярности, защиту от накрутки и включение неопубликованного контента определить при разработке соответствующего сервиса.
- **Кэш публичных профилей и метаданных:** использовать при подтверждённой нагрузке, с TTL, инвалидацией при изменении и удалении, защитой от одновременного обновления популярных ключей. Постоянный источник данных остаётся в сервисе-владельце.
- **Ограничение частоты и счётчики:** оценить Redis для общих ограничителей и временных агрегатов. При сбоях определить поведение отдельно для каждого действия; защита входа и восстановления не должна молча отключаться.
- **Очереди:** рассматривать только по потребности. Очередь отправки подтверждений уже надёжно записывается в PostgreSQL; перенос без анализа потери сообщений и повторов не требуется.

## Платный и приватный контент

Кэш должен учитывать владельца данных, видимость, блокировки, подписку и отзыв доступа. До выдачи закрытого материала проверять актуальные права; один только TTL кэша не гарантирует немедленный отзыв. Не складывать сами медиафайлы, пароли, платёжные реквизиты или долгоживущие токены в общий кэш. Для публичных рейтингов не раскрывать приватные данные и активность.

## Границы безопасности

Сессионные данные и вытесняемый кэш имеют разные требования к сохранности и политике памяти: оценить отдельные инстансы или иное реальное разделение ресурсов, а не полагаться только на разные префиксы ключей. Настроить ACL, изоляцию сети, TLS для удалённых соединений, лимиты памяти, наблюдаемость и процедуру восстановления. Политика `noeviction` предотвращает вытеснение, но при нехватке памяти приводит к ошибкам записи.

Redis по умолчанию реплицирует асинхронно; при failover возможна потеря даже подтверждённых записей. Поэтому нельзя считать простое удаление Redis-ключа достаточной гарантией, что отозванная сессия не вернётся после восстановления старого состояния. Реализованный кэш не принимает решений о доступе и всегда проверяет PostgreSQL. До возможного полного переноса источника прав в Redis нужно отдельно решить сохранность отзывов, сетевые разделения и миграцию; текущий кэш такой перенос не выполняет.
